# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Development
npm run check:now     # TypeScript + Svelte type checking

# Building
npm run build         # Full production build

# Testing
npm run test:run      # Vitest unit tests (`npm test` is the same in watch mode)
npm run test:sweep    # The corpus sweeps, kept out of the default run
npm run test:all      # Both of the above
npm run end2end       # Playwright e2e tests (builds first; requires Firebase emulator)
npm run end2end:quick # ...without rebuilding, when build/ is already current
npm run end2end:failed# ...only what failed last run

# Localization
npm run locales       # Verify locale files
npm run locales-drift # Report translations whose en-US source changed after they did
npm run locales-fix   # Auto-fix locale issues
npm run locales-translate-parallel # Auto-translate unwritten strings
npm run create-schemas # Derive schema for locale files from TypeScript

# Fonts
npm run fonts         # Verify font artifacts are in sync (also runs in npm test)
npm run fonts-fix     # Regenerate font artifacts from the manifest + font files
npm run fonts-download # Fetch new fonts declared in the manifest from Google

# Wiki
npm run wiki          # Clone or refresh the contributor wiki into ./wiki
```

**Font data is generated, never hand-edited.** Every font is declared once in [src/basis/faces/fonts.manifest.ts](src/basis/faces/fonts.manifest.ts); `unicode-range`s are derived from each font file's cmap (or captured from Google's slice partition). The **committed sources** are the manifest, `fonts.lock.json` (per-file hashes + Google's captured partition), `emoji-faces.css` (the one hand-authored island, inlined via the manifest's `override` field, cmap-guarded by `emojiRange.test.ts`), `renderable.generated.ts` (the cmap-union set the glyph chooser filters against — committed because its build reads every font cmap), and `metrics.generated.ts` (each pickable face's x-height ratio and monospace flag, committed for the same reason). The **build artifacts** `faces.generated.ts`, `static/fonts/fonts.css`, and `static/fonts/fonts-fallback.css` are gitignored and regenerated by `npm run fonts-build` in `postinstall`/`build`. After adding/updating/swapping a font file or editing the manifest, run `npm run fonts-fix` (full regen incl. the renderable set); a drift test in `npm test` fails if a font file no longer matches the lockfile. Generator code lives in [scripts/fonts/](scripts/fonts/).

**A typeface is described in words, and the vocabulary is translated rather than the fonts.** A face carries a `form` (a closed category, one per face) and up to two `impression` words, both **authored in the manifest**, plus a measured `ratio` and `mono` from `metrics.generated.ts` — turned into sentences by [faceWords.ts](src/basis/faces/faceWords.ts), which follows `BasicColors.ts`'s classify → render-through-locale-templates → wrapper shape. Thirty terms translate once and hold when a font is added; a description per font would not. Adding a pickable face without a `form` fails `faceWords.test.ts`. Two rules are load-bearing at the surfaces: `getFaceDescription` must carry the words because **on WebKit the rich option snippet is never rendered and that string is the option label**, and values read straight off the locale must go through `withoutAnnotations` — `concretize` strips the `$~` marker from the template but not from what you substitute into it. A phrase's spoken description gets name + form only, since it is re-spoken on every change.

**The two emoji presentation selectors are not symmetric, and the asymmetry is load-bearing.** The tokenizer strips U+FE0F (color) from the whole source and keeps U+FE0E (mono) — `withoutColorSelector` in [emoji.ts](src/unicode/emoji.ts), not `withoutVariationSelectors`. A bare emoji-default codepoint already renders in color, so FE0F distinguishes nothing, and stripping it is what lets `🔈.🌬️` in `Instruments.wp` resolve to the definition named `🌬` (22 shipped examples and 110 locale files carry FE0F; none carry FE0E). FE0E is the only way to ask for text presentation, so it has to survive — `Source.code` is regenerated from tokens, so anything the tokenizer drops is gone from the program. Names still strip both, via `NameToken`, so a name can never depend on presentation. Presentation is then applied by a **CSS class**, never by the selector alone: both font chains lead with Noto Color Emoji, so `emojiRuns` classifies each grapheme run and wraps it in `.emoji-color`, `.emoji-mono`, or `.emoji-keycap`. A mono run **keeps** its FE0E in the DOM, which is what makes copying an emoji off the stage preserve its presentation (stage copy reads the DOM; editor copy is model-based and unaffected). A per-token strip is not expressible in the tokenizer — it advances by `nextToken.text.length`, so a token shorter than the source it consumed leaves the selector to lex as a stray name — and anything constructing a token from a mono UI constant must use the bare codepoint (see `IsLocale`, which uses `GLOBE1_SYMBOL`, not `LOCALE_SYMBOL`).

**Updating emoji is its own procedure** spanning four subsystems (codepoints, per-locale names, and the Chromium + Safari color fonts) run in dependency order by a single `npm run emoji-update` (`-- --check` to see if an update is due). It's documented and automated in [scripts/emoji/README.md](scripts/emoji/README.md); the only manual step is a Safari visual QA the command prompts for.

**Logo assets are generated, never hand-edited.** The logo (a speech bubble that can "say anything": a glyph of the viewer's script in-app, a circle/triangle/square shapes face on static surfaces and while loading) has one source of geometry, [src/components/app/logoMark.ts](src/components/app/logoMark.ts), shared by [Logo.svelte](src/components/app/Logo.svelte) and the generator in [scripts/logo/](scripts/logo/). Everything in `static/icons/` (adaptive SVG favicon, PNGs, `favicon.ico`, maskable, `og-card.png`) is committed and hash-locked in `scripts/logo/logo.lock.json`; after editing the geometry, manifest, or generator, run `npm run logo-fix` (uses the pinned `@resvg/resvg-js`; never runs in CI). `npm run logo` verifies, and `logoSync.test.ts` runs the same checks in `npm test`, so a hand-edited icon or stale lock fails. The in-bubble glyph per script is the `glyph` field in [src/locale/Scripts.ts](src/locale/Scripts.ts) (`logoGlyph.test.ts` requires one for every supported locale's dominant script). The mark is always `currentColor`, decorative (`aria-hidden`) unless given a `label`, and all its motion is behavioral and `--animation-factor`-gated — never drawn into the mark itself.

**Instrument recordings are generated, never hand-added.** Every sampled zone is declared in [scripts/instruments/manifest.ts](scripts/instruments/manifest.ts) and built by `npm run instruments-build`, which fetches from CC0 libraries, processes in pure Node (no ffmpeg), and writes both `static/instruments/**` and `src/output/Music/samples.generated.ts` — all committed, along with `instruments.lock.json` recording each zone's provenance and upstream hash. `npm run instruments` verifies, and `instrumentsSync.test.ts` runs the same checks in `npm test`, so an edited mp3 or a stale zone map fails. Licences are checked per zone against `AllowedLicenses` in [verify.ts](scripts/instruments/verify.ts): CC0 and CC BY throughout, plus CC BY-SA for the dog, whose recordings have no CC0 equivalent on Commons. Because we ship derivatives, a zone built from a BY-SA recording is itself BY-SA, and `CREDITS.md` records that per file. Zone files are named by MIDI number because a `#` in a filename becomes a URL fragment at fetch time.

**The VS Code extension is generated, never hand-edited.** [.vscode/wordplay-theme/](.vscode/wordplay-theme/) is an optional, developer-installed extension that dresses this repo's editor window in the app's palette and highlights `.wp` files. All four of its generated files come from [scripts/vscode-theme/](scripts/vscode-theme/) via `npm run vscode-theme`: the two **theme** files are derived from the `--*-light`/`--*-dark` pairs in [src/app.html](src/app.html) and the token-category colors in [TokenView.svelte](src/components/editor/tokens/TokenView.svelte), and the **TextMate grammar** plus `language-configuration.json` are derived from the tokenizer's own serialized rule lists (`CodeTokenRules`/`PatternTokenRules`/`MarkupTokenRules` in [Tokenizer.ts](src/parser/Tokenizer.ts)) and [TokenCategories.ts](src/components/editor/tokens/TokenCategories.ts), so no glyph or rule order is ever retyped. `vscodeThemeSync.test.ts` and `vscodeGrammarSync.test.ts` fail in `npm test` if the committed files are stale. Text on a brand-colored surface is picked by the app's own rule (the mode's `--color-white`, falling back to `--color-black`) and the generator throws rather than emit a pair below WCAG AA. Passing `paletteContrast.test.ts` does **not** imply the theme passes, because the theme recombines the palette in three ways the app never does — text on the widget chrome (where the AA variants sit at 4.66-5.09:1, and the doc purple at 4.06:1), text under a selection tint (a highlight is a background for what it covers), and 9-11px badge labels (AA's 4.5:1 assumes ~16px, which is how the gold notification circles were the least legible thing in the window at 5.87:1). So the generator derives rather than copies: `readable()` deepens anything drawn as text until it clears AA on every surface it can land on, `weaken()` bounds each tint by the dimmest text it can cover, `pill()` deepens badge fills to 7:1, and `hovered()` moves a filled control's own hue away from its label instead of switching hue. `vscodeThemeContrast.test.ts` measures the generated files and requires every foreground to be classified — text, meaningful graphic (3:1), pill (7:1), or decorative by name. The grammar is **symbols-only** — localized keyword words aren't colored, since a static grammar can't read a project's declared locales — and its scopes are chosen so that a stock theme colors `.wp` sensibly while this theme's existing scope families give the app's own colors; the sync test checks the mapping, but not the regexes, which are verified by eye (see the extension README). Note that `SymType` is the union of Sym *values*, and three collide (`_` is Placeholder/Underline/LanguageJoin, `/` is Italic/Language, `^` is Extra/Exponent), so anything keyed by `SymType` must be context-aware. It affects no build output and nothing in the app imports it.

**The unit suite runs unisolated, and `vi.mock` is the one thing that can't.** [vitest.config.ts](vitest.config.ts) declares two projects: `fast`, which runs the ~433 ordinary test files with `isolate: false`, and `isolated`, which runs the handful listed in [src/util/isolatedTests.ts](src/util/isolatedTests.ts) with isolation on. Isolation is what made this suite the long pole in CI: it re-ran the setup file's 350-module graph — and rebuilt a `Basis`, whose cache is module state — once per test file, putting ~38% of all CPU into imports rather than tests. Unisolating cut total CPU from 527s to ~220s, and the CI-shaped wall clock (4 workers) from 87s to 49s. What keeps that safe is that a module mocked with `vi.mock` **stays mocked for every later file sharing the worker**, so every mocking file is listed in `MockingTests`, and [testIsolationConvention.test.ts](src/util/testIsolationConvention.test.ts) fails if that list and the files that actually mock disagree in either direction — an unlisted mock's symptom is a confusing failure in an *unrelated* file, never in the one that caused it. `OrderSensitiveTests` is the escape hatch for a file that needs its own graph for some other reason, and it is deliberately **empty**: the one thing that needed it was `Basis.test.ts` handing the *global* `Basis.Bases` cache a synthetic locale — en-US content labelled `zh-CN` — so every later test asking for a real zh basis got English names and reported them as unknown. Isolation had been hiding that, per-file, since the cache is module state. The rule it leaves behind: **`Basis.Bases` is keyed by locale name, so a synthetic locale must never claim a shipped locale's name** (`Basis.test.ts` now uses the unshipped `zh-SG`/`zh-HK`/`zh-MO`). Prefer fixing a file's shared-state coupling over adding it to this list. **A shuffled run is the check for this class of problem**: `npx vitest run --project=fast --sequence.shuffle.files` (use `.files` — plain `--sequence.shuffle` also reorders tests *within* a file and reports unrelated fixture-mutation bugs).

## Architecture

Wordplay is a web-based programming language IDE where creators write code that produces interactive, animated typography. It is built with Svelte 5 + SvelteKit 2, TypeScript (strict, no `any`), Firebase, and Vite.

### Core pipeline

Text input → **Parser** ([src/parser/](src/parser/)) → AST nodes ([src/nodes/](src/nodes/)) → **Compiler** (`Expression.compile()`) → `Step[]` → **Evaluator** ([src/runtime/Evaluator.ts](src/runtime/Evaluator.ts)) → `Value` → **Output renderer** ([src/components/output/](src/components/output/))

1. **Tokenizer** (`Tokenizer.ts`) segments text into `Token` nodes.
2. **Parser** (`parseProgram.ts`) builds an AST of ~170+ node types rooted at `Source`.
3. **AST nodes** ([src/nodes/](src/nodes/)) are **immutable** — all fields `readonly`. Nodes do not know their parent; `Root.ts` manages parent relationships. Nodes serve as the center of everything: structure, behavior, type checking, conflict detection, and localized descriptions.
4. **Type checking**: `Expression.computeType()` infers or checks types. `Context.ts` caches analysis state and prevents cycles.
5. **Conflict detection**: `Node.computeConflicts()` finds ~50+ error types ([src/conflicts/](src/conflicts/)). `Project.analyze()` runs analysis at the project level, spanning multiple `Source` files.
6. **Compilation**: `Expression.compile()` converts each expression into a flat list of `Step`s ([src/runtime/Step.ts](src/runtime/Step.ts)).
7. **Evaluation**: `Evaluator.ts` runs the `Step` sequence, maintaining a call stack and value stack. `StreamValue`s ([src/values/](src/values/)) trigger reevaluation on each new input event.
8. **Output**: `Stage`, `Phrase`, and `Group` structure values are rendered by Svelte components in [src/components/output/](src/components/output/).

**A bare name in an evaluate's inputs fills the boolean input of that name, and the name picks the slot while scope picks only the value.** `Phrase('hi' selectable)` is `selectable: ⊤` when nothing in scope is called `selectable`, and `selectable: selectable` when a boolean is — a name that resolves to anything *else* is not a shorthand and keeps its positional meaning. [inputShorthand.ts](src/nodes/inputShorthand.ts) is the only place that decides; `Evaluate.getInputMapping` claims shorthands in a pre-pass and removes them from the positional stream, so ~25 consumers of the mapping inherit it and `Mapping.given` stays the `Reference`. Six things are load-bearing. **The boolean restriction is what makes this backward compatible**, and it was measured rather than assumed: of 241 bare-reference inputs in the shipped examples, 66 have a name matching an input of the callee (`Maze(row column state)`, `Place(x y)`) and **none of those inputs is boolean**, so no shipped program changed meaning — extending the sugar to all types would rebind all 66. The type test is `isBooleanish`, not `instanceof BooleanType`, because `Phrase.flipx` is `?|ø`. **`Reference.resolve` stays lexical-only**: making it return the input bind would give `getCorrespondingDefinition` and the two locale-retargeting passes the answer for free, but `resolveToLeaf` follows a definition's *value*, which for an input is the **default** the shorthand overrides — it would report `⊥` as the shorthand's value and hand the palette a node living *inside the basis definition* to rewrite. Keeping `resolve` lexical makes that hazard, and the `getDependencies`/`evaluateTypeGuards` ones, structurally impossible instead of guarded; the three places that do want the bind ask for it explicitly, and `getCorrespondingDefinition` is one of them because [Token.ts](src/nodes/Token.ts) localizes a name token through it — without that a shorthand's name would freeze in whatever language it was typed. **`Evaluate.withBindAs` must replace a shorthand with `Input.make(name, value)`**, never in place: a bare value binds by *position*, so the palette writing `⊥` over `Phrase('hi' selectable)` would set the *size*. **`Refer.equals` needed a `variant`** or the menu's `name: ⊤` and bare-`name` suggestions compare equal and `removeDuplicates` silently drops one. **An enclosing `.member` access puts the callee's own members in scope** (`PropertyReference.getDefinitions`), so in `Phrase('hi' x).y` a bare input name resolves to the very input it fills; that is no value the evaluator can find, so it is treated as the implicit ⊤ it would mean anywhere else. And the implicit form's ⊤ is pushed by a [Push](src/runtime/Push.ts) step at compile time — `Reference.evaluate` has no `Context` and is the hottest node in the runtime, so it must never ask.

**A leading doc documents what it touches, and the blank line under a source's doc is load-bearing.** `parseProgram` took every leading doc as the *program's*, so the first definition in a source could not be documented at all (#1374) — the defect kits made unignorable, since a kit's first export is exactly the thing a reader needs explained. A leading doc group now documents the statement it is adjacent to (separated by at most one newline), and is the program's own only when nothing adjacent can take it: a blank line follows, a `↓` borrow follows, or the source ends there. Five things are load-bearing. The unit is the **group**, not the doc — `parseDocs` already groups docs separated by ≤1 newline as locale variants of one doc, so "let the last doc attach", the other candidate in the issue, would take a translation off a source's own doc. A source may open with **several** separated groups and they are all its own, which is not generosity: the root block no longer takes docs (or it swallows what the program declined and #1374 reproduces one level down), and a doc group stranded between two others reaches `parseDocumentedExpression`, whose inner `parseExpression` cannot parse a `Bind` — one shipped example became four `UnknownName`s and an `UnparsableExpression` before the loop went in. Deciding the rule needs a **speculative parse**, and `unreadTo` cannot roll one back: `parseDoc` calls `injectNext` to split a `Words` token (that is how an example's `⭐`/`🪲` suffix is separated from the words after it), so unreading restores the original *beside* the injected one and the text after an annotated example parses twice — hence `Tokens.snapshot`/`restore`, which `nextAreOptionalDocsThen` had needed all along. `getPreferredSpaces` must **print** the blank line (`separatesProgramDocs`), because a doc printed with one newline reparses as the first statement's and `soundRevisions` then discards the revision unread, which would have made the blocks-mode "add documentation" affordance silently do nothing with no test failing. And because a creator's project is stored as source text, this is a semantic change to data already in the field that no migration can reach: a project whose opening doc touches its code loses its gallery description until its author adds a blank line, and that was chosen over a display-only fallback, which is `docsFor` reborn.

### Localization

All user-visible strings live in locale JSON files ([static/locales/](static/locales/), 26 languages) validated against a schema. `Database` exposes the active locale as a Svelte store. Nodes, conflicts, values, and APIs all define localized descriptions via `Locale.ts`. Run `npm run locales` to verify and `npm run locales-fix` to repair issues, and `npm run locales-translae` to generate translations.

When several UI locales are chosen, all UI text is echoed in each chosen locale (primary full size, the rest dimmed and successively 80% the size). This is centralized in `Locales` (`getSecondaryLocaleViews`, `getMultilingualEntries`, `getMultilingualMarkup`, `getMultilingualFrom`, and the multilingual `getPlainText`/`getMultilingualText`) and consumed by `LocalizedText` (inline), `MarkupHTMLView` (block), `Hint` (rich markup tooltips), and `TutorialView` (dialog lines). It's a no-op with one locale chosen, and suppressed in localization mode. **Render visible text via `LocalizedText`/`MarkupHTMLView`, not `getPlainText`/`getMultilingualText`** — those join all locales into one string, for `title` tooltips and other single-string echo surfaces only. **`aria-*` attributes and Announcer messages are primary-locale-only via `getPrimaryPlainText`** — screen readers speak them in one voice, so a joined label reads every language back-to-back on every focus stop. `getPrimaryPlainText` is an inventory-driven swap, not a general-purpose getter: it must stay cheap (a single primary resolution — never resolve all locales and discard), and never appears in per-frame paths (locale getters have caused performance regressions before; stage/group descriptions stay behind their frame throttles). **Anything that becomes code must use `getUnannotatedPrimaryText`**: an identifier, name, map key, font name, seed code, or comparison target, since a join like `"📍 · Posición"` is not a name a creator could type (#1228). Names for basis definitions should come from the definition itself (`locales.getName(def.names)`), not from locale text.

**`guidance` is the one field that isn't a translation.** Each locale's top-level `guidance` records, in that locale's own language, the writing conventions it follows that the glossary doesn't cover. `getCheckableLocalePairs` skips it, so it's never machine translated and never counted unwritten, and it may be empty. It's rendered and edited in localization mode via `Localizer.svelte` and the `/localize` workspace, not in the workspace's string list. Two other fields are locale-local in the same way and skipped by `getCheckableLocalePairs`: the top-level `terms` word list (validated by `checkTerms`) and each glossary term's `forms` — the plurals, conjugations, and synonyms a `@reference` to that term may use (validated by `checkGlossaryForms`, guarded from padding/truncation by `isGlossaryFormsPath`).

**A locale edit's value is a string or a list, and only one path may be a list.** A glossary term's `forms` were unreachable from the `/localize` workspace: `getKeyTemplatePairs` only walks keys that *exist* and `forms?` is optional, so for the 26 locales that had none the path was in no dropdown at all — which is why en-US was the only locale with any (#1244). A list is one thing a translator edits, so it is **one edit** carrying the whole array, in Dexie and on the wire; per-index add/remove would let two edits in one bundle fight over the same index. Three things are load-bearing. `setAtPath` ([submitLocalization.ts](functions/src/submitLocalization.ts) via [localeEditPaths.ts](functions/src/localeEditPaths.ts)) **whitelists** a list write to `glossary.<id>.forms` alone — edit keys are otherwise unvalidated, so an unrestricted list write would let any signed-in caller shrink a positional tuple like `ui.page.localize.tabs.labels` to one element — and it creates the key when a locale adopts its first form and deletes it when the last one goes, leaving the file as `checkGlossaryForms`'s own repair would. `forms` is **excluded from the workspace's string list** despite carrying the `[plain]` tag (it is `[plain]` for the *editor* and `'name'` for the *verifier* — see `classifyLocalePath`): it was already listed for en-US as a positional tuple, and a leftover `forms.0` edit sorts after a whole-list one and would either overwrite element 0 or, on a shorter list, reject the entire bundle. A glossary term's `word` and `definition` are editable **wherever the term is shown** — `GlossaryEntry` carries the affordance, so the guide's glossary and global search get it too — and both must use the explicit `overrideKey` + `sourceText` pair: a term's word and definition are read by helpers that *compute* a string from the locale (`getTermWordString`, `getTermDefinition`), and an accessor that computes rather than naming a place is exactly what `accessorToLocalePath` declines. And the per-form rules are shared rather than duplicated: [glossaryFormProblem.ts](src/locale/glossaryFormProblem.ts) is the pure checker behind both `checkGlossaryForms` (which keeps its own log messages) and the editor's live feedback, so a translator hears about a collision as they type instead of from a red pull request. Because `functions/` compiles with `rootDir: "src"` it cannot import any of this, so it keeps its own `parseOverrideKey`; [overrideKey.test.ts](src/routes/[[locale]]/localize/overrideKey.test.ts) runs both copies against one table so a drift fails a test rather than a submission. Inserting a tab in the middle of `ui.page.localize.tabs` is the one thing `locales-fix` cannot do for you: it pads a positional array by **appending**, so every locale's existing labels have to be shifted into their new slots by hand or each one ends up labelling the wrong tab.

**A concretized markup reports the template it came from, which is what makes a conflict's prose editable in place.** The editor's annotations are composed — a conflict's name is one locale path, its explanation another, and the explanation is a template with the offending code substituted into it — so none of it could be reached from localization mode (#1275). `Locales.concretize`, given an *accessor*, records `{accessor, inputs}` on the `Markup` it returns (`MarkupSource` in [Markup.ts](src/nodes/Markup.ts)), and [MarkupHTMLView](src/components/concepts/MarkupHTMLView.svelte) derives one `source` from whichever markup form it was handed — bare accessor, `[accessor, inputs]`, `{perLocale}`, or an explicit `overrideKey` — so all four become editable through one path, and 68 conflicts and ~170 step explanations needed no change at all. Four rules are load-bearing. A caller that **resolved its own template** has to hand its accessor over deliberately, which `Node.getDescription` and `getDocLocales` do (making node descriptions and built-in docs editable wherever they render); the raw-string form stays inert on purpose, which is what keeps `Hint` out — an editor inside something that closes on pointer-leave is unusable, and a tip already has its own 💭 badge via `LocalizedText`'s `tipIcon`. A **fragment** drops the source (`clone`, `asLine`, `asFirstParagraph`, `firstSentenceOf`), because saving an edit made against `ConceptPreview`'s first-sentence hint would overwrite a whole multi-paragraph doc with one sentence; `Markup.concretize` otherwise **inherits** it, which is what carries a doc's origin through `Docs.getMarkup`'s input-free re-concretize. An override is **re-concretized** with the same inputs for display, so an edited template still reads like the message instead of showing `$name`. And in localization mode the markup is rendered normally with the edit affordance **beside** it rather than wrapped in a `Button`: markup can contain concept links and rendered code, which are themselves interactive, and nesting those inside a button is invalid HTML and fails axe's `nested-interactive` rule — the same reason `LinkLocalizeContext` exists for links.

**A locale path is recovered by recording, not by reading source.** [accessorToLocalePath](src/components/localization/accessorToLocalePath.ts) runs the accessor against a Proxy that records the property path it walks, which is what lets a *composed* accessor be reflected: `(l) => UnknownName.LocalePath(l).explanation`, `(l) => annotation.conflict(l).name`, and any ternary all matched nothing under the old source-text regex, so their edit buttons rendered and `commitEdit` silently discarded every edit. The regex survives as a fallback for an accessor that wraps a locale value in a call, and the derived path is **validated against en-US** before being returned — which is what closes a corruption path, not just a dead button: the regex stopped at a `[`, so a computed key like `(l) => l.ui.output.permission[item.permission]` reflected as its *parent object*, and `setAtPath` writes `parent[leafKey] = value` with no type check, so a submitted edit under that key would replace a whole subtree with one string. Two consequences. An accessor that **branches on locale content** records the branch the recorder takes, not the real one (a recorder is truthy and answers `in` as present), so choose between two literal accessors *outside* the lambda using the same test that picked the template, as `Node.getDescription` does. And `LocalizedText` renders no affordance at all when no key resolves, so a button that cannot save can never appear again.

**Locale type declarations** ([src/locale/\*.ts](src/locale/), e.g. `UITexts.ts`, `NodeTexts.ts`, `OutputTexts.ts`) describe the shape of every locale JSON file. **Every field whose value is a user-visible string MUST have a TSDoc comment containing exactly one formatting tag**, which tells the in-app localization editor which editor to render:

| Tag           | Editor           | Use when the value is...                                                                                                    |
| ------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `[plain]`     | plain-text field | a simple label, tooltip, or ARIA description                                                                                |
| `[formatted]` | Wordplay markup  | rich text rendered as `Markup` (use the `FormattedText` alias)                                                              |
| `[name]`      | name validator   | a valid Wordplay identifier or list of names (use `NameText`; never tag display labels with it — spaces are fine in labels) |
| `[emotion]`   | emotion picker   | an emotion identifier                                                                                                       |

The tag goes in the comment (e.g. `/** [plain] Tooltip for the X button */`); the TypeScript alias should match (`FormattedText` for `[formatted]`, `NameText` for `[name]`, plain `string` for `[plain]`/`[emotion]`). Fields without a recognized tag are filtered out of the editor and invisible to translators, so **every new localization key needs both a comment and a tag**. The matching logic lives in [src/components/localization/Localizer.svelte](src/components/localization/Localizer.svelte) (`getEditorType`).

The tags also determine how the locale tooling treats **string arrays** ([src/util/verify-locales/classifyLocalePath.ts](src/util/verify-locales/classifyLocalePath.ts)): `[plain]` arrays are positional tuples (e.g. `ModeText.labels`) whose length must match en-US, while `[formatted]` and `[name]` arrays (paragraph lists and name aliases) may vary in length per locale (`input.Key.keys.*` synonym lists and `glossary.*.forms` are special-cased as name-like despite their `[plain]` tag). A `[formatted]` array element must never contain a blank line (`\n\n`) outside `\…\` example code — paragraph breaks are the element boundaries — and its write-status annotation (`$?`/`$!`/`$~`) goes on the **first element only**, since the array is one document and the runtime (`Locales.get`) only inspects the first element. `npm run locales` checks these invariants and `npm run locales-fix` repairs them.

**Identifier fields are scoped by the `NameText` type, not by key name.** Fields typed `NameText` (`names`, `basis.*.name`, basis type variables like `kind`/`out`/`key`, `output.Easing.*`) become real `Names` via `getNameLocales`, so each value must be a single name or operator token; `checkNames.ts` validates this in every locale (values copied verbatim from en-US, like the symbolic `⊤⊥`, are trusted) and the fixer/translator repair via `toValidName` (which folds spaces, `_`, and hyphens/dashes into camelCase). Display labels merely named `name` (`NodeText.name`, `ConflictText.name`) are `[plain]` labels where spaces are legitimate — never fold or name-validate them. **The same rule holds for `[emotion]`**, and it was learned the hard way twice: `getCheckableLocalePairs` and the translation pass both filtered on `pair.key === 'emotion'`, meant for the 126 `[emotion]`-tagged enum values (`serious`, `curious`) that must never be translated — and `ui.localize.emotion` is a `[plain]` ARIA label that merely shares the key, so it was invisible to the verifier, the translator, and the localization workspace, and shipped as the English "Choose an emotion" in all 29 locales. Both now use `isEmotionPath`, which reads the tag. Keeping the real `[emotion]` fields excluded is load-bearing: `createUnwrittenLocale` marks every checkable pair `$?`, so a new locale would otherwise machine-translate the enum value and break it. (`Locales.ts` keeps a key-name check for the same purpose, and rightly: it walks bare objects with no path to classify, and a `$?` there only decides whether a locale counts as written.)

**A locale never repeats a name en-US already declares.** Every project's basis appends the en-US fallback, so an en-US name binds whatever the project declares — a locale listing the same string binds nothing extra, and it reads as translatable, which is how ~3,500 entries ended up asking reviewers to check machine "translations" of `&`, `≠`, `ø`, and `💬`. `checkRedundantNames.ts` removes a name a locale shares with en-US at the same path, but only while the locale keeps a name of its own (not shared, not `$?`): `["💬","Frase"]` becomes `["Frase"]`, while an untranslated `["🎨","Color"]` keeps `Color` so the gap stays visible, and a lone `["≠"]` stays whole. `npm run locales` warns, `npm run locales-fix` removes. Name arrays are exempt from the positional-array padding, so a shortened one stays shortened.

**A glossary word is introduced the first time a reader meets it, and the unit is the scene.** en-US `guidance` already said to use "a glossary reference the first time you use shared vocabulary like value or expression", but nothing enforced it, so the words a lesson leans on arrived late or never: measured over the tutorial in reading order, `type` was first used 107 paragraphs before it was first linked, `value` 22, `stage` 14, and `operator`, `loop`, and `side effect` never were. That is #960 — a reader meets "stream" as load-bearing jargon with no way to ask what it means that doesn't leave the lesson, which is what makes the glossary the right instrument: `TermView` answers hover, keyboard focus, **and click**, so unlike a concept link it works on touch and never navigates away. [glossaryLinks.ts](src/util/verify-locales/glossaryLinks.ts) links first use in `locales-fix` and warns in `locales`, over tutorial dialog (per **scene**, since a scene is what a reader lands on) and concept `doc` fields (per doc, which is also what the annotations panel quotes, so a term introduced there becomes a tappable definition in the editor's inspector). Four things are load-bearing. **First use, not every use**: `value` was already a term and still appeared bare 143 times against 41 links, so linking every occurrence would carpet the prose in dotted underlines and make the affordance invisible through repetition. The pass is **deterministic and per locale** — each locale's own word and `forms`, no model — and `drift.ts` `canonicalize` now compares with glossary references stripped (`withoutGlossaryReferences`), because adding an `@` moves no meaning; without that the first run marked 1144 strings `$!` and queued them all for paid re-translation, which is the whole cost the pass exists to avoid. Concept links are deliberately *not* stripped there — `@Phrase` becoming `@Group` is a change of subject. And **a homograph is excluded, not guessed at**: `ExcludedTerms` extends the `EXCLUDE` set `linkGlossary.ts` kept for `start`, because a lexical scanner cannot tell "did you type something?" from "the type of a value" — all 7 tutorial matches for `type` were the verb, as were `name`, `guide`, and `loop`; with the eleven exclusions the check reports 8 findings where it otherwise reports ~150. Using `scanLiteralGlossaryTerms` at corpus scale also exposed three of its own bugs, each of which had been corrupting the localization workspace's live suggestions too: `CONCEPT_RE` matched only a reference's head, so `@Phrase.name` became `@Phrase.@name`; a `<label@url>` web link was unprotected, so `<2-letter code@https://…>` gained an `@` and stopped being a link; and `isWordChar` omitted `\p{M}`, so Arabic `منطقةٔ` matched the unpointed glossary word and orphaned its hamza onto `@region`. Separately, an example **nested** inside markup about markup (`` \`\'code'\`\ ``) pairs its four delimiters by alternation and leaves `'code'` looking like prose, so those 15 strings are skipped whole. The pass is whole-word, so it declines in scripts that mark no word boundary (Japanese, Chinese, Thai) and where a suffix attaches straight to the noun (Korean `스트림부터`, Turkish `akışı`); relaxing that would be worse than the gap, since zh-CN's word for stream is the single character `流` and sits inside 交流, 流行, and 物流. Those locales still get the references en-US carries, which translation protects, and a locale wanting a particular inflection linked lists it in that term's `forms`.

**A glossary word must be a word the locale's own text actually uses.** A `@term` explains a word only where that word is written, so a term whose word the prose never uses is a definition no reader can reach — de-DE's term said *Datenstrom* while its lessons said *Strom*. [checkGlossaryWords.ts](src/util/verify-locales/checkGlossaryWords.ts) splits the problem the way `checkTypedInputNames` does. `repairGlossaryWords` fixes the shapes a machine can see, because they are orthography and formatting rather than word choice, and a word in any of them can match no prose *and* be written as no reference: a parenthetical gloss (`கோவை (expression)`, 22 of them in ta-IN-LK-SG), Hebrew vowel points (15 in he-IL — the aid `checkPointedNames` strips from names, which glossary words never got because `word` is `[plain]` and not `NameText`), and a concept link left inside the word (hi-IN's `पेहला @Source`). `checkGlossaryWordUsage` reports the 21 that remain and **never repairs them**, for `checkTypedInputNames`' reason: sometimes the glossary is the mistranslation and sometimes the prose is, and only a speaker can say which — so `GlossaryWordsAreFatal` is `false` while that backlog stands, the treatment `TypedInputNamesAreFatal` gives its own. Four things are load-bearing. The **write-status marker survives** the repair (`leadingAnnotations`), since 37 of the 38 malformed words are machine translated and dropping it would claim they had been reviewed. A strip that would make two terms **share a word is refused**, because `getGlossaryFormIndex` maps one folded form to one id and a collision makes a reference silently ambiguous. The usage test is **substring, not whole-word** — the question is only whether the word appears at all, so it degrades correctly in the unspaced scripts and agglutinative languages where [glossaryLinks.ts](src/util/verify-locales/glossaryLinks.ts) declines, and absorbs inflection without needing `forms` — and it is held to en-US using the word **five or more times**, below which the signal is noise (en-US says "tutorial" once, and 24 locales phrase that one sentence differently). It shares `ExcludedTerms` with `glossaryLinks`, since a homograph is as untrustworthy here as there, and skips a word the locale merely repeats from en-US, the rule `checkRedundantNames` applies to names. The repair **compounds**: once `கோவை (expression)` became `கோவை` and `עֵרֶך` became `ערך`, the first-use pass could match them, adding 53 links in he-IL and ta-IN-LK-SG that were previously impossible — which is why the repair is wired into `verifyLocale` ahead of `checkGlossaryForms`, and the usage check into `handleLocale`, the only seam holding the locale and both tutorials at once.

**An operator keyword word must also name its Boolean function.** Each locale's `keyword.and/or/not` should be a name of `basis.Boolean.function.and/or/not` (annotation-stripped, NFC-compared, with en-US names counting since every basis appends the en-US fallback), so a typed word resolves directly rather than through the runtime's canonical-symbol fallback. `checkOperatorKeywords.ts` warns in `npm run locales` and `npm run locales-fix` adds the word as an alias, carrying the keyword's `$~` marker when it has one.

**Template inputs are always named, never numbered.** When a locale string takes runtime values, type it as `Template<['name1', 'name2', ...]>`, write `"$name"` in the JSON, and substitute via `$locales.concretize((l) => l.path, { name: value }).toText()`. Never write `$1`/`$2` or call `.replace('$1', value)` on a template string. Numbered placeholders bypass the locale verifier's typed-key check, get clobbered by auto-translators (they don't survive `npm run locales-translate`), and are illegible to translators reviewing the JSON.

**An input a noun's form depends on is a count, declared `'#name'`.** Declare it `Template<['#count']>` and write `$#count[…|…]` in the JSON, with one arm per plural form the locale has — never a bare `$count` next to a noun, which reads "1 values". The call site is unchanged (`{ count: 3 }`); the `#` says how the *template* uses the input. Arms are in the CLDR canonical order (zero, one, two, few, many, other) filtered to that locale's forms: 2 for English, 1 for Japanese, 4 for Polish, 6 for Arabic, all derived at runtime from `Intl.PluralRules` by [src/locale/plurals.ts](src/locale/plurals.ts) — the one place that knows plural rules, shared by the runtime, `npm run locales`, the translator prompt, and the localization editor. `pluralDeclarations.test.ts` fails if a count-bearing string ships without forms; a count that genuinely stands alone with no noun ("match 1 of 3", "2 selected") is listed there with its reason instead.

**After every edit to a locale or tutorial JSON file** (anything under [static/locales/](static/locales/) — including the per-locale `*-tutorial.json` and `*-emojis.json` files — or [src/locale/en-US.json](src/locale/en-US.json)), run prettier on the changed files:

```bash
npx prettier --write '<changed files>'
```

Translation tools (e.g. `npm run locales-translate`) and direct script edits often produce inconsistent indentation, trailing newlines, or escape styles that diverge from the rest of the codebase. Running prettier keeps diffs clean and avoids spurious churn on later edits.

**A translation can be complete and still be stale.** `$!` (`Revised`) queues a string for re-translation, but it has to be typed by hand and almost never is, while in-place edits to existing en-US keys land in about half of all en-US commits. `npm run locales-drift` ([drift.ts](src/util/verify-locales/drift.ts)) finds them from git alone — no machine translation, no stored baseline: a translation whose en-US source last changed *after* it did is stale by construction. Two things keep that exact: each commit is diffed against **its own parent's blob** (which `git log --raw` already carries — comparing adjacent log entries invents drift across branches), and "after" means **topological commit order**, since committer dates aren't monotonic along the DAG. `--mark` stamps `$!` on the **locale's** string, never en-US's (an en-US `$!` resets every sibling locale at that path, but drift is per-locale), so `npm run locales-translate` and `translate.yml` fix them unchanged. Marking **replaces** the existing write-status rather than stacking on it — see the next paragraph. Comparison uses `getCheckableLocalePairs` for locale files and `getTranslatableTutorialPairs` for tutorials, because a tutorial dialog line is a `[concept, emotion, …text]` tuple and index 0/1 are schema enums, not text. `name`-kind paths are reported but never auto-marked, since machine re-translating names causes cross-locale name collisions; they need a person. **Drift is checked on every verify, not just in CI.** `npm run locales` runs the cheap `--since <branch point>` comparison (two blob reads per file, about a second, so it is fine in the watch-mode verify) and warns; `npm run locales-fix` runs the same comparison and **marks** what it finds, so the ordinary repair step queues the work and the `locales-translate` that follows fixes it — which is why `translate.yml` needs `fetch-depth: 0` (a shallow clone has no branch point, so marking would silently find nothing). The pre-commit hook warns earlier still, and CI is the backstop. The full history census stays in `npm run locales-drift`, far too slow (~40s) to run on save.

**The CI gate is `--since <base>`, not the census.** A reworded en-US string whose translation was already correct re-translates to identical bytes, so value history keeps calling it stale and a slice of the census can never clear — gating on the absolute number would be a permanently red build. `--since` asks the answerable question instead ("did this change reword English and leave the translations behind?"), needs only the base commit rather than a deep clone, and runs in `unit.yml` on every PR and push to main. The pre-commit hook runs the cheaper staged-vs-HEAD warning. The census also folds in **uncommitted** edits, so running it right after a translation pass doesn't report everything you just translated — without that, `--mark` would re-queue thousands of strings that were just paid for.

**A type and the input that takes it are one word, and the pairs are derived from the basis.** en-US names the `Bubble` type and `Phrase`'s `bubble` input alike on purpose; translating each independently gave eleven locales two words, several of them unrelated (ja-JP `あわ` "froth" against `吹き出し` the speech balloon). [checkTypedInputNames.ts](src/util/verify-locales/checkTypedInputNames.ts) polices it, and the pairs are **computed, not listed**: a type annotation like `` •ø|""|`…`|🔊|🗨 `` is TypeScript, so the set is locale-independent — enumerate `shares.all`, `UnionType.enumerate()` each input `Bind`'s `type`, keep the `NameType` members (whose name is the target's en-US emoji), and keep the pairs en-US already names alike. That gives 24; a textual "the input is named like some type" rule invents 18 more (`Phrase.face` is a typeface, not the `Face` camera stream). Three rules are load-bearing. Compare the **JSON strings, never the runtime `Names`** — `getBind` prepends the en-US first name to every definition in every locale, so a runtime comparison matches through that leak. Compare **case-folded**, since en-US's own pair is `bubble`/`Bubble`. And **word choice is never repaired by the check**: sometimes the *type* is the mistranslation (tl-PH and te-IN both rendered `Form` as a paper form, te-IN rendered `Direction` as film direction), so a real divergence warns for a person and only the case where the input has no translation at all is filled in, from the word the locale already chose. The 94 that existed were unified by hand in one pass — no native speakers were available, so each is a reviewed best effort and several are noted below as uncertain; the check is what keeps the count at zero. Running it *before* the translation phases is the prevention — an unwritten typed input is named after its type rather than translated into a fresh divergence.

**Hebrew names carry no vowel points.** Niqqud is a reading aid; Hebrew is written without it and nobody types it into code, so `בּוּעָה` was an identifier no creator could enter — 400 of he-IL's 746 names were like that, applied unevenly enough that one word appeared both ways in one locale. [checkPointedNames.ts](src/util/verify-locales/checkPointedNames.ts) strips U+0591–U+05C7. Unlike the rest of #1324 a machine can do this, because it changes orthography and not the word. Two cautions: the strip is refused when the unpointed form would collide with a sibling name, since nothing else checks that two members of one definition don't share a name — and *sibling* is decided by the field's kind, not its depth: `name`/`names` identify the definition they sit on and so compete one level up, while every other `NameText` field is a member of the definition it sits directly on. Keying both off the parent put every basis type variable into one flat `basis` scope, so `basis.List.kind` and `basis.Set.kind` read as a collision though en-US names them alike on purpose (`Kind`, `Kind`), and the five he-IL names caught that way could never be stripped; and in a caseless script a global's unpointed name can collide with a word an *example* declares — Hebrew cannot tell the `Color` type from a `color` field, which English separates by capitalization alone — giving a `DuplicateName` that four he-IL examples resolved by suffixing their own name (`שורה2`), the same convention `translateProjectContent` uses when a translated name collides (`key2`, `clé2`).

**A localized example is derived content, so it is re-derived rather than trusted.** The names an example spells live at *other* locale paths — `\Phrase('a' bubble: 'hello!')\` sits in `output.Bubble.doc` while the word it must use is `output.Phrase.bubble.names` — and those are translated in different phases and often different runs. The lookup at localization time was always right (`translateProjectContent`'s named-input pass), but nothing re-ran it, so re-translating a name stranded every example that used it: nine locales shipped `UnknownInput` after #75, and ~150 inputs per locale were still spelled in English, invisible because every basis appends the en-US fallback. [retargetExampleNames.ts](src/util/verify-locales/retargetExampleNames.ts) re-derives them **deterministically** — no model, no API key — so `npm run locales-fix` repairs the divergence instead of queueing a paid re-translation of the surrounding prose, and [exampleNamesSync.test.ts](src/util/verify-locales/exampleNamesSync.test.ts) fails the `sweep` project when one goes stale. Three things are load-bearing. The en-US example is the **oracle**: an input name the locale renamed out from under no longer resolves in the localized tree at all, so the bind is resolved on the en-US side and read back at the same index in the target locale's own basis. Nodes are paired by **descriptor sequence**, and any mismatch bails — pairing past it would rename against an unrelated node — with two exceptions that were mismatches for reasons no translation caused. Markup emits one `Words` token per line, so a translation that reflowed a `¶…¶` doc's paragraph onto one line has fewer nodes while its code is untouched; doc contents are therefore left out of both the comparison and the pairing (nothing inside a doc is ever renamed). And **language tags are restored before the comparison**, because localizing an example takes them away: `withOnlyLanguage` keeps the option whose text is translated and drops its `Language`, so `\"Language"/en\` in `node.Language.doc` shipped as `\'Langue'\` in every locale — the lesson without its subject, and re-translating reproduces it exactly. The en-US oracle says what to put back: a tag naming the **source** language marks the option that *was* translated, so it becomes the reader's language, while any other tag says what the text **is** — `'hola'/es` is Spanish for every reader — so that option is restored from en-US whole, text and all, which is how sr-RS's `'конничива'/ja` became `'こんにちは'/ja` again. A dropped option or name comes back as one span from the end of the last one the locale kept, so a `Names` separator and its spacing come with it, and the locale's own word is kept even when it carries a collision-avoiding suffix (`chat2`), since restoring en-US's would reintroduce the conflict the suffix resolved. What still bails is ordinary drift (the English example changed) — though note `locales-drift` reads only the locale and tutorial files, so it queues nothing for a how-to. And the new name is **spliced by grapheme offset**, never re-serialized: `Source` counts token positions in graphemes rather than UTF-16 units, and the tokenizer strips U+FE0F from what it reads, so rebuilding an example through `toWordplay` would land mid-character or quietly turn `'🖐️'` into `'🖐'` in every locale. The same pass runs over locale files, both tutorial modes (lines paired with `alignTutorialLines`, not by index), and the `how/*.txt` sources.

**Gallery examples are localized as whole per-locale programs, opt-in per locale.** A locale's translations live at `static/examples/<locale>/<Name>.wp` (#1310) — each a complete rewrite of its en-US master by `translateProjectContent` under `preserveTagged`, so explicitly language-tagged text and names (`'un'/fr` in FrenchNumbers, Hira's kana data) ship verbatim in every locale and only untagged content translates; a text value the program compares against *anywhere* (WhatWord's `"playing"` status) is code *everywhere* it appears (`getComparedTextValues` in [translatableText.ts](src/db/projects/translatableText.ts)). Because that rewrite only renames and re-texts, a per-locale file stays node-isomorphic (outside markup) to its master — the invariant behind everything else. [verifyExamples.ts](src/util/verify-locales/verifyExamples.ts) runs the how-to pattern: a deterministic retarget pass every mode (multi-source `retargetSerializedExample`, resolving in the full project because `↓` borrows cross sources; [localizedExamplesSync.test.ts](src/util/verify-locales/localizedExamplesSync.test.ts) fails the `sweep` project when a file goes stale), per-file writes as checkpoints, and how-to-style triggers, since a `.wp` can't carry `$?`/`$~` — missing file, byte-equal to English, structurally divergent from the master, or `+example:<Name>` under override. **Locales are opt-in**: only a `static/examples/<locale>/` directory participates, and an explicit `+example` flag on a translate run is what opts one in, so a bare `locales-translate <locale>` never silently buys 75 files; on failure nothing is written, since a missing file falls back to the master at load. Source-header names are kept verbatim from the master (a `↓ borrow` names a source and nothing retargets borrow tokens; per-locale files declare their locale through `parseSerializedProject`'s explicit `locales` override instead). At load, `getExample(id, locales)` serves one chosen locale's file directly and composites several by grapheme splice ([compositeExample.ts](src/examples/compositeExample.ts), **dynamically imported** — `examples.ts` sits on every page's static graph and the import budget is why); the composite tags the base's own-language options with the base locale wherever a secondary differs, because `getPreferred` walks the viewer's locales in order and an untagged option never *matches* — left untagged, the primary language loses to any tagged secondary. `ProjectsDatabase` evicts cached example projects when the chosen locales change, and a misaligned secondary is dropped whole, never partially merged. The `.wp` serializer is [serializeExample.ts](src/examples/serializeExample.ts) (`Project.toWordplay()` drops the preview-glyph line, so it is not the inverse of `parseSerializedProject`).

**`splitMarkupAndCode` decides what a translator may touch, so anything it mis-parses ships in English.** Two constructs were leaving an example "open", after which the entire rest of the string was classified as code — protected from translation, invisible to `hasOutOfExampleBreak`, and un-splittable by `splitDocParagraphs`. A **`¶…¶` doc inside an example is prose**, so a possessive apostrophe in it (`\¶I remember people's name…¶\`) made the quote count odd and swallowed everything after; `hasUnclosedText` twenty lines below already had this exact rule and its docstring claimed to mirror the splitter, so the fix was to make that true. An **external example** (`\py| a = 5\js| let a = 5;\`) is tag-first and carries several `\` of its own, so toggling on each one never closed it; the splitter now consumes it whole via the tokenizer's own `ExternalExamplePattern`. The cost of the gap was silent and large: `node.Doc.doc` shipped 9 of its 14 paragraphs in **every** locale, with the missing five concatenated into one English element, and `node.Example.doc`, `node.DocumentedExpression.doc`, and `node.ExternalExample.doc` the same — while `npm run locales` stayed green, because the check that would have caught it is built on the splitter. Two consequences to keep. A markup array that a **split grows** is re-queued with `$!` by `checkStringArrays` (`keepOrPlacehold`'s distinction: keep the translation, redo the document), since the uncovered paragraphs are untranslated by construction and would otherwise be unannotated, which reads as "written". And `restoreConceptLinks` now **tidies the horizontal whitespace around a restored link** — models pad a masked placeholder, which restores to double spaces and a floating `@Pose .` — touching only spaces and tabs, never a newline, and letting only `.`/`,` lose a preceding space, since French requires one before `;:!?`.

**A translation that is still the English and says so nowhere is invisible to everything.** `translationEcho.test.ts` asks whether a `$~` claim is true; [checkUntranslated.ts](src/util/verify-locales/checkUntranslated.ts) asks the opposite question, about strings nobody claims anything about. A value byte-identical to its en-US source with **no** write status reads to the rest of the tooling as hand-written English, so it is neither counted unwritten nor ever queued — three UI strings sat that way in all 29 locales since the day each was added. "Still English" is only evidence when the string is prose, so the test is narrow: two or more ASCII words, no `$` template input (a template is identical everywhere by design), and never a `name` path (`checkRedundantNames` owns those, and a locale rightly repeats an operator or emoji). Across the whole corpus that leaves six paths, two of which — `ui.font.app`/`ui.font.code`, literal font family names — are exempt by path with their reason inline.

**A translation reduced to only its `$input` says nothing, and the worst of them are silent rather than wrong.** A string that dropped every word around its input is invisible to everything: it isn't unwritten, isn't byte-identical to English, and still carries its input, so the schema, `checkUntranslated`, and `checkTemplateInputs` all pass it. ja-JP rendered both "collapse $name" and "expand $name" as `$name`, and as-IN rendered a thirty-word conflict resolution as `$expected !`. When the two strings are a pair that must differ, the defect is not merely wrong but **inaudible** — the Announcer drops a consecutive duplicate, so the second keystroke produces no speech at all, which is the "every recurring announcement must vary its text" rule arriving through the locale data instead of through the code. Two checks close it, and both skip a string already queued (`$?`/`$!`) for `findDialogDelimiterProblems`' reason — known broken and scheduled — which is what lets each be fatal rather than another standing backlog: `fix` marks a finding `$!`, so `locales-fix` queues it and the next `locales-translate` redoes it. [checkReducedTemplates.ts](src/util/verify-locales/checkReducedTemplates.ts) is scoped by the **schema**, to the fields `getDeclaredInputs` says are Template-typed, and requires en-US to carry a **content** word around its inputs — measured over the corpus the bare rule finds 44 and this one finds 34, and everything the looser rule added was a language legitimately dropping a function word ("They $description." → "$description." in five pro-drop languages, "$first and $second" → "$first、$second", "is $type" → "$type"). The word list is English and only ever applied to the **en-US source**, which is exactly right: the question it answers is whether English carries meaning here beyond the input. [checkOppositeStrings.ts](src/util/verify-locales/checkOppositeStrings.ts) asks the same thing from the reader's side, deriving its pairs **from the keys** — en-US names these in opposing pairs on purpose (`formatOn`/`formatOff`, `point.added`/`point.removed`, `fold.collapsed`/`fold.expanded`), so 64 pairs fall out of the convention table and a new one needs no maintenance. Restricting to `On`/`Off`, which the two strings that prompted this happened to use, would have found five pairs and no defects at all; the general form — *any* two siblings whose en-US differs must differ in a translation — is measurably unshippable at 418 findings, nearly all legitimate synonym collapses (`token.Link` and `token.URL` are both "رابط" in Arabic). Opposite keys are the subset where an identical translation cannot be right, and it reports five. Repair queues **both** members, since which one lost the distinction isn't knowable from here and `keepOrPlacehold` already protects a failed re-translation; a re-translation can reproduce the collision, because the model sees each string alone, and the check then fails the build again, which is the gate working. ja-JP's fold four were repaired by hand instead, from that locale's own vocabulary — its `fold.all`/`fold.none` and `feedback.foldedAll`/`unfoldedAll` siblings already carried the right verbs and register — keeping their `$~`, the way `ui.markup.feedback.formatOn`/`formatOff` was fixed.

**Only plain text can be handed to a translator and put back.** A `TextLiteral`'s segments are not all tokens — an interpolation (`'hi \name\'`) is an expression and a `@Concept` inside the text is a link node — and `translateProjectContent` read a literal's text by keeping only `Token` segments, then wrote the translation back over the whole thing. So `'hello \name\'` became `'hello '` and `'@U/192'` became `''`: the interpolation's `\…\` vanished, the example's delimiters no longer balanced, and the caller discarded the entire localized example. That is the origin of most "unbalanced delimiter" and lost-`@link` reports, not the model. A literal whose segments aren't all tokens is now left untranslated (its references are still retargeted), because losing one string's localization beats corrupting the program around it.

**A project's source language is per unit, not per run.** A project may be written in several languages, so the language a translatable unit is *in* is its own `/lang` tag; the language the creator picks in the Languages dialog covers only what carries no tag. One `from` for the whole project is #653: a bind named only `gato/es` in an en-primary project matched neither `isLanguage('en')` nor `!hasLanguage()`, so it was **skipped in silence**, and a literal with no en option fell through to `getOptions()[0]` and was sent to the model *labelled* en. [translationSources.ts](src/db/projects/translationSources.ts) is the whole selection rule, pure over nodes and locales so it costs microseconds to test, and its ladder reproduces the old rule **first, byte for byte** — the new steps fire only where the old code returned `undefined` or mislabelled a fallback, which is what makes the change purely additive. Six things are load-bearing. Grouping is **per unit, not per option**: a literal with both `/en` and `/es` needs one translation, so a unit picks one source option and that option's tag is its bucket. A **multilingual tag buckets as itself** — `/es_en` is sent as `from: 'es_en'`, needing no schema change since `localeToString` already serializes it and `from` is a string — because reducing it to its primary would drop the half the tag exists to declare; but membership (`getLanguages()`) is right for the `existingNames` *reservation* set, where over-reserving costs at most a numeric suffix and under-reserving costs the whole run to a duplicate name. A tag naming **no region adopts the declared locale** of that language, so `/es` and a declared `es-ES` are one bucket rather than two. Every bucket is **issued before any is awaited**, because the locale CLI's gather pass ([ClaudeTranslator.ts](src/util/verify-locales/ClaudeTranslator.ts) `collectExampleTexts`) records what it is asked for and returns `null` for everything — a loop stopping at the first failure would collect only the first language's strings, and the apply pass would then ask the pool for strings it had never seen. Only **every** bucket failing is a failed translation; one failed bucket keeps the others, the guarantee a failed chunk already made. And translations are keyed by **source locale and then text**, since `'no'` in English and `'no'` in French are two strings to translate, not one. Note the two non-`preserveTagged` consumers: the dialog and that CLI example-localization path, so this rule reaches every `npm run locales-translate` run, not just the app.

**Progress accumulates per run, not per call.** `getFirebaseTranslator` is constructed once per `translateProject`, so an instance *is* a run — and a run is now several calls, one per source language. Reporting each call's own `texts.length` as `total` walks the count backwards between buckets and re-says what it just said, which the announcer's queued lane drops as a consecutive duplicate: the bar stalls and the run goes silent. `runTotal`/`runDone`/`runKept` accumulate across calls instead, which for a single call is byte-for-byte the per-call numbers it replaces. Anything that reuses a translator instance across two runs inherits the first run's counts.

**A how-to has no write status, so `+howto:<id>` is its re-translation trigger.** A how-to's `.txt` carries no `$~` anywhere, which means `override && isMachineTranslated(target)` is false for *every* translated how-to: a translation that came back damaged could not be redone by any means short of deleting the file. `howToNeedsTranslation` now also fires when the file was **named explicitly** with `+howto:<id>` under `override` — naming one has already answered the question the byte-equality heuristic exists to answer ("which of these 36 do I redo?"). Re-translating is not always the repair, though: the damage that motivated this — English glue left beside a restored `@link`, "the" transliterated to a bare Devanagari `द` — is reproduced by the next run, because nothing validates it. The spacing half is now fixed deterministically in `restoreConceptLinks`; the rest still needs a person. **English is the skeleton, and a translation is a source of parts** ([#1365](https://github.com/wordplaydev/wordplay/issues/1365)). `translateHowToFile` used to run `parseHowTo` over the *target* and replace each prose run in that tree, so the output was always node-for-node the shape of the input: a translation missing half its paragraphs re-translated to one still missing them, and anything *added* to an en-US how-to was unreachable by translation entirely — measured, en-US `move-between-content` parses to 74 prose runs and 13 examples where de-DE had 20 and 3, and a full `+howto:` run over all 30 locales moved de-DE by nine lines and left it at 51% of the English. It now parses English for structure and pairs the target's paragraphs against it ([pairHowTo.ts](src/util/verify-locales/pairHowTo.ts)) with the LCS `syncTutorialStructure` already uses, keyed on a signature that counts a paragraph's untranslated marks — its `@Concept` links, its `\…\` examples — and treats a *run* of adjacent prose as one, since how many `Words` tokens a paragraph has is a fact about line wrapping. A kept paragraph's prose and localized examples are reused and only what English has beyond them is bought, so the repair costs the missing parts rather than the corpus. `+howto:<id>` under `override` still means "buy this whole file again".

**Rewriting a how-to means passing its spaces back, or the file is destroyed.** A markup `Words` token stops at every newline, so a paragraph's soft line breaks live in the `Spaces` map rather than in any token's text — the model never sees them and cannot lose them. `parseHowTo` used to build its markup with `parseLocaleDoc`, which reports no spacing, and `howToToString` then asked `getPreferredSpaces` to invent some from an empty map; since `Paragraph.segments` declares none, every segment in a paragraph was joined with **nothing**. Measured: 36 of the 37 en-US how-tos came back damaged from a *no-op* parse-and-serialize, every locale had lost 74 of 74 intra-paragraph line breaks, and that is what ran translated sentences together (`…pointing.Let's try…`, #1364) and flattened every block example onto one line. `parseHowTo` now returns the tokenizer's own `Spaces` and `howToToString` takes them, which round-trips all 37 exactly (modulo the FE0F strip the tokenizer applies to all source). Three rules follow. A node **kept from the translation brings its own spaces** (`Spaces.withSpaces`), since the map is keyed by token identity and English has no entry for a token it never parsed. A **replaced** token needs `Spaces.withReplacement`, or its preceding space is orphaned. And a kept example is laid out from **English** (`spacingLike`), which is the only copy whose formatting the old serializer never flattened. Separately, a `Words` token holds its own *intra-line* spaces, which the model does return trimmed: `padLike` restores them from the source token, and adds a boundary where English had none but the translation needs one — German writes `@Row machen, die…` where English writes `@Row, which…`.

**A garbled translation is retried alone before being given up on.** Every rejection in `translate()` — dropped `⟦n⟧` placeholder, unbalanced delimiter, residual mask — is the model losing track in a 25-segment request, and it does that far less in a request holding one string. `ClaudeTranslator` re-translates just the failures one at a time and re-validates; without it the same strings failed every run forever. The first attempt stays quiet so one string doesn't report two problems.

**Chunk requests by characters, not just segment count.** A request's cost is the text in it, and 25 short segments differ from 25 long ones by an order of magnitude. On the slowest scripts a chunk runs ~0.045s per source character, so an 8,000-character chunk blew the 600s client timeout three times and lost half an hour of work, while 4,400 characters took ~200s. `chunkUnits` ([ClaudeTranslator.ts](src/util/verify-locales/ClaudeTranslator.ts)) bounds a request by both `CHUNK_SIZE` and `CHUNK_CHARACTERS`; Latin-script locales rarely reach the character budget, so they keep filling all 25 segments.

**Translation runs on a cheap model with an expensive safety net.** `DEFAULT_MODEL` (Sonnet, 2.5× cheaper than Opus per token in both directions) carries prose, docs, and examples; `REPAIR_MODEL` (Opus) handles only the work where a mistake is costly or already happened — glossary words and construct names (the `options.names` flag on `Translator.translate`, set by `translateLocale`'s name phases, because a bad name is a cross-locale collision) and the per-string retries of strings the default model garbled. The downstream validators (delimiters, concept links, residual masks, example conflict checks) are what make the cheap default safe: garbles are caught and escalated, not shipped. **Thinking is disabled on the bulk path** — left alone, the default model reasons adaptively, and on one Kannada slice it spent 10k of 17k output tokens thinking about a routine chunk, erasing its price advantage entirely ($0.26 vs Opus's $0.24); with thinking off the same slice cost $0.13 with the same zero-garble result, and ran faster. The repair model keeps its default, since it gets exactly the strings that needed more than mechanics. Both models are env-overridable (`WORDPLAY_TRANSLATOR_MODEL`, `WORDPLAY_TRANSLATOR_REPAIR_MODEL`), and every translate run ends with per-model token usage — including thinking tokens, so this regression is visible if it returns — and an estimated cost (prices are pinned in `ClaudeTranslator.ts` with a checked date — verify against the pricing page when touching them); `batch.ts` sums its children via the `[translator-usage]` stdout marker line, which is machine-parsed, so its format must stay stable.

**One translator instance per run, and example localization is pooled.** `start.ts` constructs the backend once and threads it through `verifyLocale`, `verifyTutorial`, and `verifyHowTo` (which previously built one per how-to file — 36 per locale), so the localized-example cache spans every file: an example appearing in both the locale file and the tutorial is localized once. Localizing examples used to be one request per unique example — a few short identifiers riding the full system prompt, ~900 requests per locale and most of a run's input tokens. It is now three passes: a **gather** pass runs `translateProjectContent` with a recording translator (returning `null` aborts it before any tree rewriting) to learn each example's translatable texts; the union is translated once through the normal bounded chunks; an **apply** pass re-runs with a lookup translator. This relies on extraction being deterministic — `translateProjectContent.test.ts` proves gather+lookup ≡ one direct pass. Identical units are also deduplicated inside every `translate()` call (`translateDeduped`), and a non-markup array path re-sends only the elements that are actually queued (`itemNeedsTranslation`), keeping good sibling translations instead of re-buying them; markup arrays stay whole-document, since their elements are paragraphs of one doc.

**A `@Concept` link is masked as `⟦n⟧` while it's translated, and the restore must be forgiving.** A model rewriting a sentence into another script doesn't always hand the placeholder back verbatim — it transliterates the digit into that script's numerals (`⟦೦⟧`), pads it, or swaps the brackets — and `\d` under `/u` matches only ASCII 0-9, so any of those silently failed: the link vanished, or the raw placeholder shipped to a reader. `LinkMaskPattern` now accepts `\p{Nd}` digits, surrounding space, and look-alike brackets, and normalizes the digits ([protect.ts](src/util/verify-locales/protect.ts)); ASCII `[…]` is deliberately excluded, since real markup uses it (`$value[true|false]`). `hasResidualLinkMask` then refuses any translation that still carries a placeholder — `mismatchedConceptLinks` can't catch that on its own, because when the source has no links of its own both sides count zero and the `⟦0⟧` sails through.

**A translation run checkpoints, and `$~` is what makes the checkpoint durable.** A new locale is ~1.5 hours and ~$3 of paid work, and it used to reach disk exactly once: `verifyLocale` performs no writes at all, so the whole tree was held in memory until `handleLocale` wrote it after the last phase, and a process killed at 25% lost 25% of the money. `translateLocale` now takes a `checkpoint` callback and calls it after each phase and after each `CHECKPOINT_PATHS`-sized slice of the bulk phase (`verifyTutorial` does the same, per mode; how-tos already wrote per file). No new bookkeeping makes this resumable — `shouldStringBeMachineTranslated` already skips a `$~` string outside `override`, so what landed is skipped and what didn't is still `$?` and is retried. Four things are load-bearing. Slicing is only safe because the slices **partition** the paths: `indicesFor` memoizes per path and its first answer wins, so a path in two slices would send one set of array elements and write back another — everything else `apply` needs is rebuilt per call, so `translations.shift()` stays in lockstep within a slice. Slicing would otherwise **cost** money, because `translateDeduped` dedupes only within one request and a duplicate straddling a boundary would be bought twice; `translateMemoized` ([ClaudeTranslator.ts](src/util/verify-locales/ClaudeTranslator.ts)) remembers across requests, keyed on the system prompt and model, which is exactly safe because the prompt already encodes source, target, glossary, conventions, and whether the strings are glossary terms — and it now spans the locale file, both tutorials, and the 36 how-tos, which were separate calls before. `writeFormatted` writes through a temp file and renames, since a kill mid-write would otherwise leave truncated JSON that fails the next run's parse — losing the very thing the checkpoint saved. And the new-locale branch in `start.ts` tests for the locale **file**, not its folder: the folder is created before any translating, so a run killed before its first save left an empty folder that made the branch skip, while the loop above quietly ignores a folder whose JSON won't load when a focal locale is set — the same command that started the work became a silent no-op reporting zero locales and exiting 0. Resume is cheap for `$?` work but not for `$!` work: a path in `revisedStrings` re-translates unconditionally, ignoring what is on disk.

**A failed re-translation must keep the translation it had.** `translateLocale`'s failure path writes the *en-US source* marked `$?`, which is right for a string that was never translated (fall back loudly rather than ship English that looks translated) and destructive for one being re-translated — it throws the existing translation away and substitutes English. That path was almost unreachable until drift detection made re-translating existing strings routine, and the first drift-marked run silently replaced 20 real translations across four languages with English. `keepOrPlacehold` ([verifyLocale.ts](src/util/verify-locales/verifyLocale.ts)) now keeps a non-empty existing translation and re-queues it with `$!`; only a string with nothing to keep becomes `$?` + English. Anything else that writes a fallback value must make the same distinction.

**A string has exactly one write-status.** `isRevised` tests `startsWith('$!')`, so `$~$!…` reads as merely machine translated: the translator skips it outside `override` and the `$!` is never honored — about a hundred strings sat in that state. `checkStringArrays` normalizes markup arrays; [checkAnnotations.ts](src/util/verify-locales/checkAnnotations.ts) does the same for scalar strings, collapsing to the highest-priority status (`$?` > `$!` > `$~`). Never prepend a marker to a value that may already have one.

**Tutorial dialog is held to the same delimiter rule as locale docs.** `findDialogDelimiterProblems` ([verifyTutorial.ts](src/util/verify-locales/verifyTutorial.ts)) compares each dialog line's `\…\` and `` `…` `` counts against its aligned en-US line, because dialog had no such check and ~190 lines across 26 locales had quietly lost the examples they teach — a sentence saying to "just use `\+\`" with no `+` in it. An **orphaned** delimiter (source count even, translation odd) and an **unclosed** literal (caught by `unclosedInCode`, shared with `translationGuards.ts`, and invisible to counting since the counts match) are hard errors unless the string is queued (`$?`/`$!`); `locales-fix`/`locales-translate` mark them `$!` so the same run repairs them. Everything else is **drift**, gated on `DelimiterDriftIsFatal`, which is now **true**: the machine-translated backlog (146 strings) was re-translated, and the last 46 — **hand-written** translations a model would only overwrite, 32 of them pt-PT's — were repaired by hand against the en-US source, so the count is zero and drift fails like everything else. Two en-US typos were repairs of their own, since every locale had faithfully copied them: `\Character>s` (a `>` for the closing `\`) and `\Place(0m 0m\)` (the `)` outside the delimiters, which no count-based check can see and which `locales-drift` caught instead). Requiring the parity *flip* rather than any mismatch matters: en-US itself ships one unclosed example, so a locale that dropped or fixed it is an improvement. Lines whose paragraph count differs are skipped — that is `syncTutorialStructure`'s job, and comparing them per-index compares unrelated sentences.

**A tour is named in one place, stepped in another, and the split is a budget.** The project view's six interface tours are named in [tours.ts](src/components/project/tours.ts) and stepped in [tourSteps.ts](src/components/project/tourSteps.ts), so a lesson can point at one with `@Tour/<id>` markup instead of describing the interface itself (#984). Four things are load-bearing. `tours.ts` has **no runtime imports at all**, because `ConceptLink` imports `isTourID` to validate a reference and the parser must never reach into components — and the *steps* are in the other module because every page reaches markup and so reaches the names, while only the project view can run a tour; keeping the step text with the names would move seven kilobytes of explanation into four pages that can't use it, which is the leak [importGraph.test.ts](src/util/importGraph.test.ts) exists to catch. A `@Tour/` naming a tour that doesn't exist is a **conflict**, unlike a `@username/character` reference, whose target isn't knowable at check time — that is what makes a typo reportable rather than a link that renders as nothing. The request travels through a **context slot**, not a launcher function, because the tutorial's dialog is a *sibling* of its ProjectView rather than a descendant, so `TutorialView` sets the slot above both and ProjectView provides its own only when nothing above it has. And a step's `uiid` is otherwise **unverified** — a target that has been renamed renders "this part of the interface isn't currently visible", which reads exactly like a control that is merely off screen, and is how the source tour's `expand` step pointed at nothing for months — so [tours.test.ts](src/components/project/tours.test.ts) sweeps the tree for every step's target and for every `@Tour/` reference in every locale.

**The tutorial's next control is held until a pointed-to tour is taken.** `TutorialView` derives the pause's pending tours from the same markup scan that produces the `@UI/` highlights, and a tour counts as taken when it is *closed*, from anywhere — the tile's ⓘ button included — recorded in the cloud-synced [ToursSetting](src/db/settings/ToursSetting.ts). Three consequences. A skip control sits under the dialog rather than in the nav row, both because that is where the choice is being made and because the nav row is a fixed three-part layout the narrow dialog column has no room to grow. The refusal is **announced** (`tutorial-tour`, in the `interrupt` lane): a keystroke that produces silence is indistinguishable from a broken app, and interrupt is the lane that re-presents identical text, which is what a repeated refusal needs — the usual "vary the words" rule can't apply, since the refusal is the same event every time. And when the gate lifts, `TutorialView` **takes focus back**: a tour opened with a pointer has nowhere to return focus to (Button's `onpointerdown` leaves it on the body), so without that a keyboard user would have to Tab back into the lesson they were just held in.

**A locale tag may be written by name, and a code always wins.** `/es`, `/Español`, and `/Spanish` are one tag, as are `/es-MX`, `/es-México`, and `/es-Mexico` (#1220). [tagNames.ts](src/locale/tagNames.ts) is the one place that decides: `foldTagName` strips case, accents, and everything that is not a letter or digit, so a name is typable in the form the fold recognizes (`BahasaIndonesia`, `CotedIvoire`). That is *nearly* closed over the token grammar but not quite: `ø` and `ƒ` are reserved symbols that are also letters, so they survive the fold and still split a name token. Three names in the whole catalogue are affected — Faroese `føroyskt` and the regions `Bouvetøya` and `Føroyar` — each still reachable by its English name, and `isTypableTagName` is what keeps an unwritable spelling out of the completion menu. Four things are load-bearing. The fold is **locale-independent** (plain `toLowerCase`, never `toLocaleLowerCase(reader)`) for the reason [casing.ts](src/unicode/casing.ts) gives — a program must mean the same thing to everyone reading it. A **code is matched before any name**, and a name that folds onto a different entry's code is never indexed at all: three language names do (Sichuan Yi's onto `yi`, Ho's onto `ho`, Lü's onto `lu`), which leaves Ho — named "Ho" in every language — the one language writable only as `/hoc`, asserted by name in `tagNames.test.ts`. The **source keeps the spelling the author chose**; only `Language`'s accessors resolve, so `/Español` round-trips. And the serializing accessors (`getTagString`, `getBCP47`) are **resolve-or-raw, never strictly resolved**: `TextValue` asks `getTagString() !== undefined` to know a value carries a tag, so filtering an unrecognized code would silently untag `'hi'/aaa`, and every `Intl` consumer downstream (`countWords`, `pattern/segment`, `collation`) already degrades a tag Intl rejects to the root locale. **Completing a tag as it is typed is a separate mechanism from resolving one**, and it needed its own hook: a tag's parts are `Sym`-typed *tokens*, and `Sym.Name` is in `WildcardSymbols`, so `getPossibleNodes` returns `[]` for every one of `Language`'s fields and no field-driven path — which is every path a text caret takes — can offer a language or region. `Language.getPossibleCompletions(anchor, edit)` is dispatched from two places in [PossibleEdits.ts](src/edit/menu/PossibleEdits.ts): a token-anchored branch in `getRelativeFieldEdits` beside the `ConceptLink` one, and an early return in `getFieldAssignments` for the blocks-mode slot. It is keyed on the **anchor token**, which is what says which part is being typed, and `fieldIsEmpty` is deliberately *not* the lever — it is only read inside `getRelativeFieldEdits` (so it cannot reach the blocks path at all), and an `Assign` and a `Replace` producing the same tag never dedupe, since each `equals` requires its own class. Completions offer the form that was typed (`/esp` → `/español`, `/span` → `/Spanish`), widen past the shipped locales only once a prefix exists, and are guarded twice: a spelling must be one name token, and it must resolve back to the code it was offered for — without that second guard, offering Sichuan Yi's name "Yi" would insert a tag meaning Yiddish. The ambiguity tests in [tagNames.test.ts](src/locale/tagNames.test.ts) are what keep a newly added language or region from quietly shadowing an existing one — a collision there is not a bug to route around, it means two entries answer to one spelling and whichever loses becomes unwritable by name.

**Region names are generated, never hand-edited.** [Regions.ts](src/locale/Regions.ts) stays the hand-authored ISO 3166 list — it anchors `RegionCode`, and its `en` values are deliberately tuned (`GB` is "UK") — while [regionNames.generated.ts](src/locale/regionNames.generated.ts) adds each region's name in its own language, written by `npm run regions` from the same pinned CLDR release as the date/time and exemplar data. The choice of language is the whole design: ranking a territory's languages by CLDR's population share alone picks **English** for Belgium, Ethiopia, and South Africa, because those shares count second-language speakers, so official languages are ranked first and the unfiltered ranking is only a fallback. `de_facto_official` counts as official (it is how CLDR records Mexico's Spanish and the USA's English, neither official by statute) and `official_regional` does not (a language official in one province does not name a country). Each entry records **which language named it**, so BE→`nl` and CH→`de` are reviewable in the diff rather than mysterious, and carries CLDR's English name and alternates, which are what people actually type — ISO's "Bolivia, Plurinational State of" is not a name anyone could write in a tag, while "Bolivia", "UK", and "Ivory Coast" are. Two regions (AQ, HM) have no local language at all and fall back to English. [generateRegionNames.test.ts](src/util/verify-locales/generateRegionNames.test.ts) checks coverage, the `RegionNamesCLDR === CLDR_VERSION` provenance pin, and the ranking rule against fixtures; it reads the committed artifact rather than regenerating, since generation fetches CLDR and the `unit / locales` CI job has no budget for it.

**Several locale artifacts are generated, never hand-edited**, and all hard-fail `npm run locales`: [static/locales/names.json](static/locales/names.json), the word → locale index the languages dialog uses (built from each locale's *basis*, so it changes whenever a locale renames a definition); each locale's `<code>-how.json` bundle, built from its `how/*.txt` sources; `src/locale/choosePrompts.generated.ts`, the first-run language prompt's phrases; and `static/manifests/<code>.webmanifest`, one **web app manifest per locale** so an installed Wordplay is named in the language it was installed from (#564). `npm run locales-fix` regenerates all of them. Because the `unit / locales` CI job runs `npm ci` without a build, nothing regenerates them there — a stale artifact is a red deploy, not a self-healing one. [localeArtifactsSync.test.ts](src/util/verify-locales/localeArtifactsSync.test.ts) runs the same checks in the `sweep` project (read-only, via the generators' `write: false` path), and the pre-commit hook runs the sweep when anything under `static/locales/` or `src/locale/en-US.json` is staged, so drift is caught before the push rather than after.

**The updates page is localized by content-addressing, so an entry is bought once and never re-bought.** CHANGELOG.md is authored in English and edited three times a day, which rules out both inlining 30 translations per bullet and paying to re-translate an archive that only grows (#1164). [scripts/updates.ts](scripts/updates.ts) parses it into `static/updates.json` — release structure, emoji marker, and each entry's Markdown converted to **Wordplay markup**, the same content type as every `[formatted]` locale string — and gives each text a stable `id`, `'e' + sha256(markdown).slice(0,12)`. A locale's translations are a bare `id → markup` map at `static/locales/<code>/<code>-updates.json`, so structure is stored once rather than 29 times and a missing id falls back to English per entry. That map *is* the incrementality: an entry is new iff its id is absent, no markers to maintain and no git history to walk, and an edited entry gets a new id and re-translates alone. Six things are load-bearing. The id hashes the **Markdown**, not the generated markup, so improving `toMarkup` doesn't invalidate every translation ever bought — `BundleFormat` is the lever for when you do want that. It never starts with a digit, because `parseOverrideKey` reads a trailing all-digit segment as an array index and an edit under `updates.entries.1234` would be written into a string. Only **dated** releases are translated, since the page filters out the legacy `## 0.16.38` headings and prose no reader can reach is the one cost this design exists to avoid. `toMarkup` runs at **build time** rather than per render, which is what lets the translator's markup validators apply to exactly what the page shows — and moving it there exposed that escaping `/` before the link substitution had shipped every Markdown link as `https:////wordplay.dev//about`, on 156 entries. The bundle is **fetched**, not statically imported: it was being rendered into all 32 prerendered copies of the page, 450KB each, the same English every time. And a translation is refused unless it **parses as markup across its whole length**, the rule `checkHowToBody` enforces — though as a length comparison rather than an exact round trip, because an entry is a fragment and one that quotes a `¶` inside an example re-serializes one delimiter longer, which is printing rather than truncation.

**A changelog entry's code is syntax being described, and only its names may be localized.** `translate()` localizes an embedded `\code\` example, which is right when it renames a definition — a German reader's basis says `Rede()`, not `Speech()` — and wrong for everything else. The changelog is where that goes worst, because the entries most likely to carry code are the ones *about* syntax: the entry announcing that a language tag may be written by name shipped in German as `'hallo'` three times, having lost all three tags, and the Persian announcement shipped the locale code `fa-AF` as `fa - AF`. That is the defect the gallery-example note above records as "the lesson without its subject", arriving in a pipeline with no `retargetExampleNames` to protect it. [restoreExampleSyntax.ts](src/util/verify-locales/restoreExampleSyntax.ts) is the cheap protection — deterministic, no model — and it decides per span by **token shape with names blanked and spacing kept**: same shape means only names changed, so it stands; anything else is restored from English. Spacing is in the shape on purpose, because `fa-AF` and `fa - AF` tokenize identically and only the spacing says which is the locale code. Splitting on the delimiter is exact because `mismatchedDelimiter` has already refused any translation whose count differs, so odd indices are code in both and correspond. It runs on each translation *before* it is stored and again over what is on disk under `locales-fix`, so a run can neither ship this damage nor leave it.

**The archive was condensed once, deliberately, and the rules that did it are kept.** 447 of the 511 multi-sentence entries were rewritten to a single short sentence before the 29-locale backfill (152,254 → 117,689 characters), finishing a job begun by hand in `324cf14`. Two things from that pass are worth keeping in mind. **Cut size is not a proxy for lost meaning** — the first attempt dropped a whole behavior at a 36% cut and only an explanation at 59% — so the model is required to *declare* what it removed and to name a reason for any second sentence, which is what makes a bulk rewrite reviewable by scanning rather than by diffing. And [condenseRules.ts](scripts/condenseRules.ts) refuses a rewrite that drops a `` `code` `` span, a link, or a `(#N)` citation, compared as multisets: those are the only parts of an entry a reader can act on, so a condensation that cuts a clause carrying one has cut the wrong clause. [changelogStructure.test.ts](src/util/verify-locales/changelogStructure.test.ts) is the gate that class of edit never had — CHANGELOG.md is in no pre-commit trigger, and `verifyChangelog`'s markup check only runs under `npm run locales` against a gitignored artifact, which is how `324cf14` shipped an entry whose code span became an unbalanced Example.

**A `<label@url>` target was the one construct reaching a translator unprotected.** `ConceptRegExPattern` deliberately refuses an `@` before `http://`, `https://`, or `mailto:`, so `protectConceptLinks` masked `@Concept` references and nothing masked a web link's URL — and no validator checked one came back. `protectLinks` ([protect.ts](src/util/verify-locales/protect.ts)) masks both, and `mismatchedWebLinks` refuses a translation that dropped, invented, or rewrote a target. Three ordering rules. Targets are masked **before** concept links, because `ConceptPattern` is the raw pattern without the tokenizer's email-boundary rule and would otherwise eat the `@x.dev` out of the middle of `<Email us@mailto:hi@x.dev>`. The concept pass then **skips a match containing the mask delimiter**, because a Wordplay name may be almost any character, so `@⟦0⟧` lexes as a concept link and masking it buries one placeholder inside another. And an **issue link is masked whole**, label included: its label is the issue number, and a model that transliterates a masked digit into Kannada numerals will do the same to a bare one. The label of any other link stays visible, since translating "About" into "Acerca de" is the point.

**Installability is manifest-only — there is deliberately no service worker.** Wordplay is already installable (Add to Home Screen / Add to Dock need no service worker, and Chrome dropped that requirement for menu install), and it is already local-first for data (`WordplayDexie` is the durable mirror; see [firebase.ts](src/db/firebase.ts)). What installing adds is worth having on its own: WebKit deletes script-written storage after 7 days without interaction and **exempts home-screen web apps**, so installing is the only thing that protects a signed-out creator's local projects. Offline *cold start* is the one thing a service worker would add, and it is not worth a second update path beside the version poll + [UpdateNotification.svelte](src/components/app/UpdateNotification.svelte), nor a cache policy every runtime-fetched asset kind would have to be reasoned about (`static/` is 223MB against a 7.4MB shell). Two consequences of installing are handled in the app rather than papered over: an iOS installed app's storage is a container **separate** from Safari's, so [projects/installedStorage.ts](src/routes/[[locale]]/projects/installedStorage.ts) gates an explanation for the signed-out, empty case; and an emailed sign-in link opens in the browser rather than the installed app, so [Login.svelte](src/routes/[[locale]]/login/Login.svelte) accepts a **pasted** link, which crosses that boundary (and covers reading the email on another device).

**Moderation is server-authoritative, and the ban is a claim, not a read.** A creator's moderation record lives at `strikes/{uid}` — server-written, client-readable, exactly the `usage/{uid}` pattern, and never on `creators/{uid}`, which the client overwrites wholesale. Reports live in their own `reports` collection because a viewer who isn't a contributor cannot write the project document at all, so a `reported` field on the project is not expressible. Everything a moderator's decision does happens in the `moderateProject` callable ([functions/src/moderateProject.ts](functions/src/moderateProject.ts)): flags, un-publishing, resolving reports, the strike count, and at the third strike the **`banned` custom claim** plus taking down what that creator already published. `firestore.rules` enforces the ban through the claim alone (`mayBePublic()`) — reading `strikes/{uid}` there would cost a document read on **every project write**, and the rules file already documents how tight that budget is. Two consequences to keep: a function that sets claims must **spread the existing ones** (`setCustomUserClaims` replaces the whole object, so writing `{banned:true}` alone strips `mod`/`teacher` — [scripts/claims.js](scripts/claims.js) does the same), and because a claim only reaches a session on token refresh, the client watches its own record and calls `getIdToken(true)` when it changes.

**A character is in at most one gallery, and the rules are why.** A gallery holds characters as well as projects (#822) — not a second, parallel kind of gallery, which would be a second set of permissions to learn and to keep from drifting. `Character.gallery` is the source of truth and `Gallery.characters` is the index built from it, both written in one batch the way `addProject` does, and the gallery page renders from the **character** side so a share appears without waiting for the gallery document. One gallery rather than several is not a preference: security rules have no loop, so several would need a server-maintained flat viewer list rebuilt on every membership change, where one costs a single `get()` — ordered *after* the owner/collaborator/mod tests so it's only paid when nothing cheaper already allowed the read. Three asymmetries are deliberate. A public gallery grants read to a **signed-out** visitor, one step further than `canReadProject`, whose gallery grant sits inside its auth guard and so admits a signed-in stranger but not an anonymous one — an artifact of where that guard sits, and applied here it would blank a public gallery's characters for exactly the audience `public` is for. A curator **cannot edit** a character in their gallery though they can edit a project there: sharing a drawing isn't handing it over, and the remedy is removal, which is a write to the *gallery* document. And a **remix carries no gallery**, like a remixed project. `CharactersDatabase` streams gallery-mates' characters through chunked `where('gallery','in',...)` listeners exactly like `ProjectsDatabase`, with the same `GALLERY_CHUNK_SIZE` reason, and removal is decided against the **union** of every listener — a character leaving the gallery query is still yours, and a per-snapshot `removed` would evict it. Reads are no longer gated on being signed in (#742): the rules always allowed a public character, and the guard meant *no* character resolved for a visitor, so a public project using one showed an empty box.

**A creator's character names must be unique, and only the name is held back.** Uniqueness is on the **full** `username/Name`, among characters you **own** — that is what `byName` and the `where('name','==',…)` lookup are keyed on, so two creators naming one `Dog` collide with nothing while one creator doing so makes `@them/Dog` resolve to whichever document the query returns last. The check it replaced compared **bare** names across everything you could *edit*, so collaborating on `bob/Dog` wrongly reported `Dog` as taken. It was also never enforced — `savable` omitted it despite a comment promising otherwise — and the fix is emphatically not to gate `savable` on it: that would stop saving **shapes** too, so a creator who typed a colliding name would silently lose every stroke drawn afterwards while the editor showed a notice about the name. Only `editedCharacter`'s `name` falls back to `persisted.name`. One consequence for tests: e2e tests sharing one account must give their characters distinct names, or the second one's name is correctly discarded and the tile renders unnamed.

**Folders are split across two documents on purpose.** Membership (`Project.folder`, a folder ID) is on the project doc so it merges per-field across devices; the folder's own name and collapsed state are creator settings, so renaming one is a single write rather than a rewrite of every project it holds, and an empty folder can exist before anything is in it. The cost is that the two halves sync independently — `resolveFolders` puts a project whose folder hasn't arrived yet at the top level rather than hiding it. Anything added to `SettingsSchema` must land with its `syncUser` read and its `toObject` write **in the same change**, or the next write of any other setting silently drops it.

**A bare email address in markup is a link.** `hi@wordplay.dev` lexes as one `Sym.URL` token and renders as a `mailto:` link; `<Email us@mailto:hi@x.dev>` works too. Two rules make that possible and both are load-bearing: `ConceptRegExPattern` refuses an `@` that directly follows an email local part (the rule plain text literals always had, finally applied to markup) and exempts `mailto:` the way it already exempted `http://`; and the markup tokenizer looks ahead for an address and cuts the preceding words run at its local part, since `@` is a markup symbol and words always stop before it. Every path that turns a URL token into an `href` goes through [linkHref.ts](src/parser/linkHref.ts), which adds the `mailto:` scheme, keeps the schemeless `://path` internal-link convention, and **allowlists schemes** — documentation is creator-authored and shown to everyone, so a `javascript:` URL must never become an anchor.

**The translation cap lives at the callable, not the feature.** `getLLMTranslations` bills per call, so it requires a signed-in caller and reserves characters against `usage/{uid}` before the model runs ([functions/src/translationBudget.ts](functions/src/translationBudget.ts), `DAILY_TRANSLATION_CHARACTERS`; the client mirrors the number for display only and [translationBudgetSync.test.ts](src/db/translationBudgetSync.test.ts) fails if they drift). Anything new that translates should go through [getFirebaseTranslator](src/db/getFirebaseTranslator.ts) — the one `RawTranslator` that chunks, reports progress, and classifies a budget rejection into [translationBudget.svelte.ts](src/db/translationBudget.svelte.ts) — and drop in `TranslationMeter`, rather than calling the callable itself. `usage/{uid}` is server-written and client-readable by design: never put a counter on `creators/{uid}`, which is client-writable and overwritten wholesale by `uploadSettings`.

**Text that becomes code must not be translated.** A creator's `key = 'ArrowLeft'`, a map key, or an emoji literal is data, and giving it a target-language option (then making that locale primary) silently changes what the program does — it is what made a translated Heart Attack unplayable (#1276), and the same rule as #1228. [translatableText.ts](src/db/projects/translatableText.ts) is the single place that decides; extend it rather than adding a check at a call site. **Adding a translation must not rewrite the program**: the `replace` flag (the dialog's add/rewrite mode) gates all reference, `NameType`, and `Input` retargeting, and adding a name appends rather than calling `Names.withName`, which replaces an *untagged* name and so deleted the creator's own word. Retargeting always asks for a **non-symbolic** name — asking for "any name in that language" returns whatever the locale lists first, which is often an emoji. And a guard meant for code must not be run over prose: `'` opens a text literal in code and is just an apostrophe in a doc, so `translationProblem` checks only inside `\code\`. Renaming has two non-obvious reaches of its own, both regression-tested in [translateStructures.test.ts](src/db/projects/translateStructures.test.ts): a `NameType` (`zombie•Zombie`) names its definition but is not a `Reference`, so it needs its own retargeting pass, and a translated name must avoid the **target locale's basis names** as well as the project's own — the locale brings definitions into scope that the project's source never mentions.

**A kit is one published source, and immutability is what makes borrowing it cheap.** `↓ @amy/colors 3` names a kit (#8) — owner-scoped like a character, `@`-prefixed because `/` is the language tag and `↓ start/en` would otherwise be ambiguous with a borrow of a source written in English, and versioned by the numeral `BORROW` has parsed since long before anything read it. The language barely changed, because every borrow funnels through one synchronous call, `Project.getShare`, which already searched the project's sources and then the basis; kits are a third tier. What could **not** change is that it is synchronous — analysis and evaluation both resolve borrows without being able to await — so a kit is fetched and parsed into a `Source` **before** the `Project` that uses it is built (`resolveKits`, then `withDependencies`). This is deliberately not how `@username/Character` works: a character resolves asynchronously in a Svelte component and degrades to an empty box, which is fine for a decoration and impossible for code. Seven things are load-bearing. The schema is **split** — `kits/{id}` is the small mutable registry entry, `kitversions/{id}_{n}` the code — and a version is immutable, so it is cached in IndexedDB **permanently and never invalidated**, its `public` and `owner` are denormalized onto it, and its read rule is a field test with **zero `get()`s**; that is what keeps resolving borrows off the rules' ~10-document budget (the constraint behind `GALLERY_CHUNK_SIZE = 8`) and means a class of thirty sharing one kit costs thirty reads *ever*. There are also **no listeners on a consumed kit**, unlike every other shareable type. The **two `public` flags do different jobs** — `kit.public` governs discovery, `version.public` governs resolution — so withdrawing a kit stops new people finding it without breaking programs that already borrow it, and only moderation clears the versions, which `applyRemedy` must do in the same batch or a taken-down kit keeps running everywhere. A **conversion cannot travel by name** (`Convert` matches types, and `ConversionDefinition` isn't even in the `Definition` union), so a kit's `↑` conversions become ambient in whatever source borrowed it, folded into the three gather sites — gating on the borrow is what stops them leaking. Imports are **flat**, and namespacing them is #1373 rather than part of this: the tempting shortcut, materializing a kit as a `StructureDefinition` with statics the way `Color.red` works, fails because `isStatic` exists only on `Bind` and `FunctionDefinition`, `↑ •Inner()` inside a structure parses cleanly and silently does nothing, and a dotted *type* annotation isn't expressible. The kit database is **dynamically imported** (`DB.loadKits()`) for the reason `loadProjects` is, and wiring it as an eager field put it on all five page graphs. And a new sync domain must **report itself settled**: `Kits` in `SyncDomains` without a `startSync` arm left the save-status footer spinning on every page, because it spins while any domain is `initializing`.

**Three kits ship with Wordplay, as files rather than documents.** `@wordplay/alphabets`, `@wordplay/instruments` and `@wordplay/tunes` live at `src/db/kits/sources/<name>/<version>.wp`, are listed by a literal in [builtins.ts](src/db/kits/builtins.ts), and are built into registry entries in memory the way `getExampleGalleries` builds the seven example galleries — nothing about them is in Firestore, because everything this repo ships is a file registered by a literal in `src/`. Their sources are **imported, not fetched** (a kit that fails to load makes someone's *own* project report `UnknownKit`), which is why they sit under `src/` rather than beside the examples in `static/`: a `?raw` import inlines them into the `loadKits` chunk, and `static/` would deploy a second copy of the same 236 KB that nothing ever requests. Resolution needs no new tier, since `getByName` and `getVersion` early-return from `byName`/`versions` — **seeding those caches is the mechanism**, and seeding first means a cloud kit can never shadow a built-in by name. So `seedBuiltins` must re-run at the end of `clear()`, and a built-in is never persisted to Dexie, where it would outlive its release. A shipped version's file is never edited; an improvement is a new file. Shipping through git *is* the moderation decision, so `builtinKits.test.ts` is what a moderator would have been — including that a doc claiming a count must be counting the data beside it, which caught a Russian alphabet shipping 32 letters under a doc claiming 33. Two rules govern a kit's examples and its types. A worked example of a kit's function names that function, and `ExampleUI` builds a self-contained project from the example alone — so a kit's page reported `FunctionException` on the very examples documenting it. The **`ExampleScope` context** fixes it: `KitView` supplies a prelude (`↓ @owner/name version`) and the already-resolved dependency, the prelude is prepended to the example *and shown with it* (it is part of what a reader copies), and it is exposed through a **getter**, never assigned in an effect — a kit loads asynchronously, so an effect sets it after the examples have mounted and built their evaluators. And a **block must expose its own statements to its own nodes whichever source is asking**: `Block.getStatementIndexContaining` used `context.source.root`, so for a node inside a borrowed kit — whose root is in `project.roots` but not in `getSources()` — nothing inside the kit could see anything else inside it. An export typed through a private helper bound and printed correctly, then halted with `FunctionException` on the first `.method()` (`Evaluate.compile` resolves its function at compile time), with no conflict anywhere. Use `context.getRoot(node) ?? context.source.root`, as `typeGuards.ts` does.

**A kit is localized in place, and four rules make that possible.** A per-locale copy is not expressible — a kit is referenced by name from other people's programs and a version stores one `code` string — so every language lives in the one source (`↑ latin/en,latín/es`, a `¶…¶/es` per doc), which `WhatWord.wp` already does and which breaks no borrow, since `Names.hasName` never consults a tag. [verifyKits.ts](src/util/verify-locales/verifyKits.ts) drives `translateProjectContent`'s **add** mode, which appends rather than replaces and skips what already has the target language, so re-running is free. The rules: a kit's **data** literals are tagged with the language they *are* and `preserveTagged` keeps them verbatim (without it the Latin alphabet got a Spanish translation); **`translateTaggedNames`** is needed because `MissingShareLanguages` forces export names to be tagged too, so tagged-ness cannot also mean "don't translate" (without it *no* export name translated); **`examples: false`**, because a backend localizes an embedded example by building a project from it alone, where a kit's own definitions resolve to nothing and the result doesn't parse; and **names inside docs are skipped in add mode**, or a throwaway lambda parameter collects an alias per locale. Two general bugs fell out: `p.toWordplay()` with no `Spaces` sent embedded examples to the translator with every space stripped (`v.icon 2m color:` → `v.icon2mcolor:`), and a shared definition's `↑` was stranded on its own line whenever it was re-spaced — `Bind`, `FunctionDefinition` and `StructureDefinition` all now keep the marker with what it marks. The pass is **in the CLI on both axes** — it enumerates kit directories from disk, so a new kit warns once per locale and a new locale once per kit, naming the fix; it warns rather than fails. Since a `.wp` carries no write status, nothing can tell a stale translation from a current one, so naming a kit under `override` is the redo trigger (as with a how-to), implemented by stripping that language and letting the add pass replace it. And kits are the one content `batch.ts` must not parallelize — a kit is one shared source each locale appends to, so `splitKitPhase` pulls it out of the parallel phase and runs it serially afterwards rather than serializing the whole sweep.

**What a published kit owes its readers is a conflict on the code, not a checklist in a dialog.** `UndocumentedShare` and `UnexampledShare` sit on each `↑` definition, `UnexampledKit` on the `Program` when nothing in the source carries a `\…\` example, and `KitCannotBorrow` on a `↓` — all four `Minor`, because the code runs perfectly and an error-level conflict would make the project count as broken, add to the error badge, and block blocks-mode edits. All four fire only in a source a project *publishes*, since `↑` also means "share with my own other sources". One implementation raises them ([publishedShare.ts](src/nodes/publishedShare.ts)) and is asked two ways: through `computeConflicts` once the project has a kit, and **hypothetically** by `checkKit` for the publish dialog — without which a project's first publish is ungated and every one after it gated, which is exactly backwards. The dialog renders those conflicts' own explanations, so a checklist and an annotation cannot drift; `validateKit` keeps only what has no node to hang on (a source that shares nothing). Four things follow. A project publishes **at most one kit**, recording the kit's **id** (`Project.getKitID`, schema v12) rather than its name — a name lookup meant the first publish after a rename matched nothing and silently created a *second* kit, and `changeUsername` now rewrites kits exactly as it rewrites characters, with `aliases` server-owned in the rules because a client that could write its own would make its kit answer to someone else's name. A kit's description is **derived** (the first sentence of its source's doc) and its preview is the `⭐` example rendered once at publish and cached on the version, evaluated in the kit's own scope — `kitPreviewSource` appends it to the kit's code, since `\Phrase(sunset)\` means what it means *there*. A kit's page is `/guide?kit=amy/colors`, its own URL param because `?concept=` splits on `/` into owner and name, rendering `kitShareConcepts` through the very views the docs tile uses so the documentation cannot look different depending on where it was found. And what documents an export is now the export's own doc, because #1374 is fixed on both halves: `Program.getScopeOfChild` scopes a source's doc to the source, so it can name what the source defines, and a leading doc **touching** what follows it documents that rather than being hoisted onto the program — so the blank line under a source's doc is load-bearing, and `docsFor`, the fallback that used to hand the program's doc to the first export, is gone along with the kit page's disagreement with the publish dialog. `makeKit`'s output is held against `kitServerFieldsInitial()` by `rulesFieldsSync.test.ts`, because that guard has nothing stored to compare against on a create — the hole galleries had (#1352) — and a refused write is silent. For the same reason the client never writes `moderation`: asking to be listed is `public`, and the `kitEdited` trigger answers.

### Dependency overrides

`package.json` is JSON, so an override can't carry its own comment (and a `"//"` key inside `overrides` would be read as an override for a package named `//`). The rationale lives here instead.

**`cookie: ^0.7.0` must not move past `^0.7`.** It exists only to patch CVE-2024-47764 (cookie <0.7.0), and `npm audit` is already clean at 0.7.2. SvelteKit imports `{ parse, serialize }` in its server runtime and `CookieSerializeOptions` in `page/types.d.ts`; cookie 1.x renamed the type and cookie 2.x removed both functions (they became `parseCookie`/`stringifyCookie`). So bumping it has no security upside and breaks Kit. Revisit only when SvelteKit's own `cookie` range moves to `^1`/`^2`.

### Immutability convention

Immutable data structures and pure functions are the norm everywhere except: Svelte components (internal state + global context), `Evaluator` (stack-based evaluation state), and `Database` (persistence). Most bugs will be in those three areas.

**Adapting project output to a dark canvas is one decision per stage, not one per color.** A viewer in dark mode can have a bright stage flipped dark (`adaptOutput`), and the transform is an LCh **lightness inversion** — `L → 1 − L`, hue and chroma untouched ([adapt.ts](src/output/Color/adapt.ts)). Not the hue complement the issue proposed (it changes what every color *is* and darkens nothing) and not dimming (measured: it loses WCAG AA on 20% of pairs and drops the default black-on-white from 21:1 to 6.6:1, where inversion keeps 21:1). Inversion preserves every pair's |ΔL\*| exactly and is an exact involution, which is what makes the setting a true toggle and what lets [PhotosensitivityAnalysis](src/output/PhotosensitivityAnalysis.ts) go on measuring authored values. Because contrast is a **relationship**, adapting some of a stage's colors and not others is exactly what would destroy it, so: the flag rides on `RenderContext` and `getColorCSS` **requires** it rather than defaulting (a call site can't silently forget); the decision is **latched per `Evaluator`** in `OutputView` so an animated background can't flip the palette mid-run, while a revision — which builds a new `Evaluator` — re-decides so palette editing stays live; and `OutputAnimation` applies it to WAAPI keyframes, which never pass through Svelte markup. It fires only above `AdaptationLightnessThreshold` (**0.8, not 0.5**) because WCAG's ratio is not symmetric about mid lightness — its flare term makes dark-on-mid beat light-on-mid — so a mid-toned stage loses measurably more than a bright one (worst ratio a passing pair falls to: 3.24 at L=0.6 against 4.25 at L=0.8), and a mid-toned stage is not the blinding rectangle the feature exists for. Two consequences elsewhere. Persisted project previews ([extractPreview.ts](src/components/app/extractPreview.ts) writes CSS *strings* into the project document) must be adapted **at render** ([adaptPreview.ts](src/components/app/adaptPreview.ts)), never at extract, or one viewer's setting ships to everyone — and that path parses `lch()` with a regex rather than `ColorJS`, because pulling colorjs.io onto every route with a project tile blew the [import budget](src/util/importGraph.test.ts). The music renderings are excluded on purpose: `LightShow` and `Mood` hold lightness and opacity **constant** as their flash-safety invariant, so adapting them would move the one quantity that must not move. Separately from the setting, every output surface now declares the `color-scheme` of the canvas it **actually paints** instead of pinning `light`, so theme-token fallbacks (a `Shape`'s untinted fill, a `Group`'s frame, the stage's own foreground) resolve against the creator's background — which also fixes a standing bug for projects that author a dark background.

**Markup is edited as a `Source`, and prose mode is a rendering rather than a preview.** The markup editor (#1307) wraps a markup string in the doc delimiter — `markupToSource` in [markupSource.ts](src/edit/markup/markupSource.ts) — so `Caret`, `RootView`, `CaretView`, the keyboard mirror, IME, and the announcer all apply to prose unchanged, and an `\1 + 1\` example is already in the same token stream, which is why editing embedded code needed no second mechanism. The wrapper is **unconditional**, unlike `toMarkup`'s, whose "skip if it already starts with `¶`" guard is what makes `Hello ¶note¶` parse as an empty doc followed by code — fine for rendering, but an editor that lost text to it would lose the creator's work. Measured over the 321,561 shipped strings: all but 7 round-trip, 1,321 of those differ only by the U+FE0F normalization the tokenizer applies to all source, and `canRepresent` declines the rest (5 carry an unclosed container delimiter — `¶`, `` ` ``, or `\` — and 2 carry zero-width spaces) so a surface falls back to a plain field rather than silently rewriting a translator's string. **`text` is written back only from `apply`**, never on mount, for the same reason. Prose mode hides delimiters through `RootView`'s **existing** hidden-node set (the one that hides non-preferred locale tags), so a hidden token keeps its place in the DOM at zero size with `aria-hidden` and the caret can still land on it; it reveals the run the caret is inside, which is what makes the syntax learnable in place and what keeps two caret positions from collapsing onto one pixel. Three things are load-bearing elsewhere. The command list is composed **markup-first**, then the code editor's `Category.Cursor` motion, deleting by key, and the typing catch-all last, because `handleKeyCommand` takes the first match — without the borrowed motion commands the arrows do nothing, and with the catch-all early it shadows everything. `handleInput` must **return** after clearing `skipNextInput`, or the command and the browser's own field edit both apply and every character is typed twice. And the editor must never reach a page's static import graph: `FormattedEditor` is rendered by `MarkupHTMLView` on every page, so it imports the editor **dynamically** and the toolbar is rendered from *inside* the editor rather than beside it — a static import of the command list puts the whole language runtime on all five page graphs, which is what [importGraph.test.ts](src/util/importGraph.test.ts)'s runtime-reachability test exists to catch.

**Markup has no aside, and a `¶` used as one silently truncates the document.** `toMarkup` wraps a body in `¶…¶` to put the tokenizer in markup mode, so a `¶` the author writes closes that wrapper and everything after it parses as code — unrendered, unreported, and invisible to `npm run locales`. The same is true of a lone `` ` `` (it opens a formatted literal) and an odd number of `\`. en-US's `move-between-content` how-to used `¶…¶` for a "Note:" block and shipped **1,229 of its 2,143 characters**; worse, the translator was handed the truncated half too, so **28 of its 30 translations stop where the aside began**, averaging 55% of the English. `checkHowToBody` ([buildHowTos.ts](src/util/verify-locales/buildHowTos.ts)) now fails a body whose parse doesn't cover it, which is what makes this reportable rather than silent. An aside is written as an ordinary paragraph; a literal backtick is doubled (the markup escape rule). Note the shape trap when repairing one: a `¶…¶` immediately after a `\` on its own line is a **doc on the code inside an example** and entirely legitimate — `choose-adventure` and `layering-images` both use it — so only a `¶` outside an example is the bug. The 28 truncated translations were rebuilt in #547 and the exemption they had in [exampleNamesSync.test.ts](src/util/verify-locales/exampleNamesSync.test.ts) is gone. What no longer needs a workaround is the repair: see the rule below on English being the skeleton.

**Soft wrap has to reach the renderer, not just the CSS.** The editor renders every space as U+00A0 so a line holds its shape while it is edited, and `RootView`'s `wrap` prop is what turns that off. `Editor.svelte` set the `.wrap` class but **never passed the prop**, so every space stayed non-breaking and a line could only ever break at the `<wbr>` `NodeView` emits *between* tokens — which means a long token could not wrap at all: measured, a 2,330px line stayed 2,330px inside a 315px viewport with wrapping on, and the tile scrolled instead. Passing it is the whole fix; the `min-width: fit-content` on `.annotated-editor` and the tokens' `display: inline-block` both look like culprits and neither is, because the code's own min-content collapses once its spaces can break. The context also had to become a **store**: held as a plain boolean it froze at whatever the setting was when the view mounted, so toggling wrap on afterwards changed the CSS and left the spaces non-breaking. One residual, worth knowing rather than chasing: after a toggle the virtualized renderer's scroll extent stays stale until the next keystroke, though the text itself wraps immediately.

**Prose mode is a rendering of the same tokens, so what makes it prose is CSS that lives where the code styling does.** The code font is re-asserted per token by `.token-view`, not only on `.root`, and `TokenCategories` maps `Sym.Words` to *literal* — so a markup editor rendered through `RootView` shows every word of a paragraph in the code font and the literal colour. `format.prose` is threaded through `Format` and read by the views that own those declarations. Three rules are load-bearing beyond the obvious font and colour. **A token must be `display: inline`** in the markup editor, in *both* modes: the tokenizer emits one `Sym.Words` token per run between delimiters, so a paragraph is often a single token, and an `inline-block` is an atomic inline that cannot split — a paragraph following a bold run moved to the next line whole rather than continuing after it. **A hidden delimiter must stay `inline-block`**, because `.hide` collapses a token by zeroing its box and width and height do not apply to an inline — making tokens inline is what made prose mode show every `*` it was supposed to hide. And **an `Example`'s program is rendered with `prose: false`** (`ExampleView`), so code inside prose keeps the code font and its syntax colours, which is what the read-only view shows and what saves every downstream rule from carving out an exception.

**Per-token state belongs on `Format`, not in a context.** The editor's cost is dominated by what every token does, so anything a token reads on each render is a per-token multiplier. Soft wrap needs to be *reactive* — it is a setting toggled while the editor is open, and a plain context value froze at mount — but making the context a store gave every token a subscription: **measured at +0.26ms per keystroke over 306 tokens, about 5% of the editor's typing cost**, which reverting it confirmed almost exactly. `Format` is already threaded to every node view and already recreated per render, so carrying `wrapping` there is reactive *and* free; the `getWrapping`/`setWrapping` context is gone. Same rule as the `CaretTokenSummary` note above: resolve once in the editor, hand tokens a value.

**Two editors share a spine, and the input layer is where they can rot.** `Caret`, `RootView`, `CaretView`, `PointerUtilities`, the `Highlight` machinery, and the whole `Command` apparatus are single implementations both editors use; `Editor.svelte` is the full one (windowing, drag, conflicts, menu, blocks) and `MarkupEditor.svelte` a restricted one. What is *duplicated* is the ~150-line input layer — the mirror write, the composition lifecycle, paste — because the two genuinely differ there: the markup editor offsets every mirror position by its `¶` wrapper, has no blocks mode, routes `historyUndo` to its own history, and has no internal clipboard. The three shipped bug fixes that layer encodes are therefore extracted as *rules* rather than left in two copies: `shouldEchoNatively` (#1248), `caretFieldSelection` (#1329), and `isComposingKeyDown` (#1054) each have one implementation and unit tests. What keeps the remaining glue honest is coverage, not the `KEEP IN SYNC` markers: [ime-composition.spec.ts](tests/end2end/ime-composition.spec.ts) runs Latin, Korean, Japanese, and stuck-composition recovery against **both** editors, parameterized by which editor's mirror to compose into — a bare `document.querySelector('textarea.keyboard-input')` finds the code editor's, since the project view mounts both. That coverage is the point: a composition that silently drops syllables still renders and still saves, so only a CJK creator would ever see it, and for a while the markup editor's copy of those handlers had no test at all.

**An editor is more than a caret model.** The markup editor's first pass had the model and the commands right and shipped almost none of the experience, and each gap was a thing the host never declared rather than anything architectural. The hidden mirror needs **`pointer-events: none`**, or it covers the editor and `document.elementFromPoint` — which every pointer caret-placement helper calls — returns the textarea, so no click can ever place the caret. The container needs **`isolation: isolate`**, or a selection highlight's below-layer `z-index: -1` escapes and paints behind the host's background. It needs a **`line-height`**, because a token's box is its line box and the caret takes its height from that box, so inheriting a prose host's line-height made the caret as tall as a paragraph. The vertical-movement commands need **`view` and `getTokenViews` on `CommandContext`** — they `return false` without them, which makes `handleKeyCommand` keep scanning, so not even the DOM-free `moveLineVertical` fallback runs. And `CaretView` reads the **singular** `setEditor` context to know it is focused; with only `setEditors` (plural) the caret renders permanently at `opacity: 0.25`. `outline.ts` finds an outline's origin with `closest('.editor, .markup-editor')`; a host that matches neither gets viewport coordinates inside a relatively-positioned box, and the highlight lands somewhere else on the page entirely.

**A token's box is the union of every line it covers, and in prose a token is a paragraph.** Nine reported defects in the markup editor were one defect: caret placement, selection outlines, pointer hit-testing and vertical motion all measured a token with `getBoundingClientRect`. In code that is a single line box and the two agree; the markup tokenizer emits one `Sym.Words` token per run between delimiters, so a paragraph is usually one `display: inline` token wrapping across many lines, and everything measured from it was as tall as the passage — a paragraph-tall caret at every paragraph start, a one-word selection outlined around six lines, and a click resolved by interpolating `textLength × (extent / totalExtent)`, which is exact only for monospace on one line. `getClientRects()` is the question the union box cannot answer: one rect per line fragment, and **exactly one for a token that doesn't wrap**, so the fix is shared and unconditional rather than branched on `format.prose` — code is byte-identical, and soft-wrapped code, which had the same latent bug, is fixed too. [measureTokenSegment.ts](src/components/editor/highlights/measureTokenSegment.ts) grew `segmentLineRects` (per-line rects for a span) and `graphemeOffsetAt` (a binary search over collapsed-range positions, block axis first so a click on the third line resolves to that line rather than the same fraction along the first). Four things are worth keeping. The search **hoists the tree walk and the grapheme segmentation out of the loop** — `locateCaretRect` does both per call, and doing them a dozen times per vertical arrow press cost +40%, which the shared `graphemeTable` brings to +11%; typing is unaffected, since a collapsed caret measures once. `CaretView`'s `lineHeight` fallback was the union box **and cached**, so the first token measured poisoned every later caret — its `<br>` probe never matches in text mode, because `NodeView` renders the break in the *sibling* `.space` span. The end-of-document caret resolves to the `¶` wrapper, which is never rendered, so it re-anchors to the previous token — by that token's union box, which put it at the far edge of the *first* line; `edgeOfToken` measures the last line's rect instead, and takes it from a **non-collapsed** range, because Chromium reports no rects at all for a collapsed range at the very end of a text node. And `outline.ts` still had two `closest('.editor')` lookups that are `null` in the markup editor, so inter-paragraph whitespace was silently dropped from every selection.

**A caret is not a selection, and both have to survive an edit.** Three unrelated causes made a selection look broken. The outline was traced in a `$derived`, which runs **before** Svelte commits the DOM — it resolves nodes by id, and an edit gives every node a new id, so after bolding a selection it found nothing and drew nothing. That is why the caret "disappeared" on bold: `CaretView` hides itself for a range by design, and the outline meant to replace it never appeared. It is now `$effect` + `tick()`, as `Editor.svelte`'s search outlines already were. Second, `Caret.isIn` returned `false` for *every* range, so selecting text collapsed every reveal at once — the `*…*` just inserted re-hid itself, and a web link snapped back to an anchor; a range is now "in" a node when the node contains both ends, which is also right in the code editor. Third, `Caret.delete`'s range branch returns `[newSource, caretOnTheOldSource]`, and the markup editor's `apply` read only the caret's source — so selecting text and pressing Backspace moved the caret and changed nothing. Anything applying a borrowed command's `[Source, Caret]` must take the source from the tuple.

**Word motion did not exist anywhere in the app, and `pointerdown` carries no click count.** The code editor's arrows step *token* boundaries, which coincides with words often enough to look like word motion and is not. `moveByWord` and `wordAt` build on [getWordInfo](src/runtime/pattern/segment.ts), which already wraps `Intl.Segmenter`, already degrades a malformed language tag, and — the reason to reuse it rather than call the segmenter — already returns its boundaries in **grapheme indices**, the unit `Caret.position` counts in. Forward lands on the end of the next word and backward on the start of the previous one, skipping the punctuation between, which is what every platform does; stepping every segmenter boundary would stop three times in `Wordplay. `. It is bound to Alt/Option+Arrow, and Control/Command+Arrow takes the line boundary — not for the affordance but because an unmatched chord bubbles out of the editor and `Control+ArrowLeft` is the timeline's step, the same defect as `Control+Home`. Double- and triple-click count their own clicks: `detail` is a MouseEvent notion that `pointerdown` reports as 0 in Chromium, and where a platform *does* populate it, it continues that platform's own click chain — so trusting it made a double-click after an earlier caret-placing click select the paragraph. Same conclusion `Editor.svelte` reached for the same reason.

**A caret at the end of a paragraph is a caret in the space, not in a token.** The `\n` between paragraphs is *space*, so that caret takes `CaretView`'s space branch rather than the text one — and that branch anchored its inline coordinate to `priorTokenBox.inlineEnd`, the union box again. On a wrapped paragraph whose last line is short, the caret was drawn at the *widest* line's right edge on the *last* line's row: past the end of the text, by 385px in the case measured. `edgeOfToken` gives the end of the prior token's last line instead. Worth knowing that this is a different branch from the one an end-of-*document* caret takes, and that both had the same cause.

**A link that isn't an anchor still has to look like a link.** Dropping the `<a>` in prose — which had to go, since it swallowed the `pointerdown` that places the caret — left web links and bare emails rendering as ordinary text, with only the markup the editor hides to distinguish them. Both now carry the link colour and an underline without being anchors: `WebLinkView` styles its whole run (delimiters included, so a revealed link reads as one thing), and `TokenView` marks a bare URL or email `link`. Two rules there. The styling must **out-specify the prose neutralization**, which is an attribute selector (`[class*='token-category-']`), or it is silently overridden. And splitting "is a URL" from "renders as an anchor" is what makes the bare-email case work at all: `linkedURL` consulted `$caret`, which the markup editor never provides — `MarkupEditor` does not call `setCaret`, deliberately, since every rendered `TokenView` would then subscribe to it — so the caret test was always false there and an email was *permanently* an anchor, unclickable and uneditable.

**An empty document renders nothing, so the caret had nothing to anchor to.** Every branch of `CaretView.computePlacement` resolves a token view, and an empty markup has not one token — so a blank composer showed no caret at all and read as unfocusable, even though it had focus and typing worked. `atContentStart` places it at the content's start instead. It is gated on `getTokenViews().length === 0` rather than on the token view being missing, because a token that is merely **scrolled out of the virtualization window** also has no view, and the windowing code depends on getting no placement so it can scroll the caret in — drawing it at the top-left would both misplace it and suppress the scroll.

**The mode switch is a toggle, because it has two states and a button shows neither.** `ui.markup.mode` already existed, unused, with exactly the two strings a `ToggleText` wants, and the tip names the action from whichever mode you are in. The control routes through the same `onToggleMode` the mode *command* calls rather than setting the mode itself, so the button and Control+Enter cannot disagree, and `aria-pressed` tracks either path. `CaretView` also takes `prose` as a **reflow signal** — not a setting it reads, but a statement that showing or hiding every delimiter moves all the geometry under the caret. Note this was added on report and is unverified: measured in the composer, the caret's position and height already tracked the mode within 30ms by both paths, so the staleness reproduces somewhere this doesn't cover.

**Tab always leaves the markup editor.** An unmatched keystroke has its default prevented so the browser cannot edit the mirrored field behind the model's back, and Tab was caught by that. `role="application"` offers no other way out, so consuming it is a keyboard trap — and unlike the code editor, prose has no use for an inserted tab worth trading that for.

**A link with no URL is not a link.** `insertWebLink` used to splice `<label@>`, and a `Sym.URL` token needs `://` and a character after it — so that is not a `WebLink` at all: it is prose that renders its own angle brackets (the reported "inserts some invisible markup"), and the next character typed makes `@h` lex as a **concept reference**, after which further letters were refused. It now inserts IANA's reserved `https://example.com` with the URL **selected**, so the link parses from the moment it exists and typing replaces the placeholder. Separately, prose mode no longer swaps in an `<a>`: an anchor stops the `pointerdown` that would place the caret, so a link was a hole in the text that could never be entered or edited, and it was a Tab stop inside `role="application"` — the hazard `ConceptLinkView` documents avoiding. `markupHidden.ts` hides everything but the description and reveals it at the caret, the rule bold and italic already follow.

**`Source.reparse`'s fast path could silently swallow a typed character, and the reason is still unknown.** `tryTextOnlyEdit` handles the common case — one token's text changes, no boundary moves — by replacing that token in the existing tree. When the replacement doesn't land the tree comes back unchanged, and because `Source.code` is regenerated from the AST, the character simply never appears: typing a URL into a markup link dropped every letter after the first. It reproduces only in the browser, never under vitest with the same sequence of edits, and when it happens the token list and the program's leaves are the same instances in the same order — so `replace` finding nothing is unexplained. The guard is right regardless: verify the edit landed and fall through to the full reparse, which is always correct and costs O(1) (`fast.tokens` is already the new program's leaves).

**Example annotations apply next to an example, not only inside it.** `enclosingExample` asked `getTokenAt(span[0])`, whose predicate is `position < index + length`, so a caret one past the closing `\` resolved to the prose *after* the example — which is exactly where the `⭐` and `🪲` it toggles are rendered. Asymmetrically, too: with an annotation already there, that token's parent *is* the example, so removing one worked where adding one did not. The token **ending** at the position counts as well, the ordinary adjacency rule.

**The markup toolbar's groups are the command list.** [MarkupToolbarGroups](src/components/editor/markup/MarkupCommands.ts) is the single source of order for both the toolbar and what the keyboard dispatches, which is safe because no two markup commands share a shortcut (asserted). Undo and redo lead; the example insert sits with the annotations it produces rather than with the formatting, and those four annotations are **hidden** outside an example rather than greyed, because an annotation is a statement about an example and four permanently grey buttons read as broken. They stay `active`-gated so the *shortcut* is still consumed and explained. The visibility is decided from a **debounced settled caret**, the reason `Command.where` gives: the caret publishes on every keystroke, and a toolbar whose item count changes that often makes `OverflowToolbar` re-measure every item and can reshuffle the hamburger out from under the pointer. The group rule is [Separator.svelte](src/components/project/Separator.svelte) — which already existed and was unused — carried inside the first item of each group so it is measured with it, and hidden in the overflow panel, where a stretched vertical rule in a column of buttons reads as a stray mark.

**Prose motion is not code motion, and an unmatched keystroke is not harmless.** Four defects survived every unit and e2e test the markup editor had and only appeared when a whole multi-paragraph passage was written end to end, which is the argument for doing that at least once per editing surface. **Arrows must move by character**: the code editor's `moveInlineText` selects the *node* the caret steps onto — right for picking out a subexpression, bewildering in a paragraph — and the `¶` wrapper makes the end of the text a token boundary always, so one ArrowLeft from the end selected the whole sentence and the Shift+ArrowLeft after it extended by node, wrapping an entire paragraph in `*` where a word had been selected. `moveByCharacter` ([formatOperations.ts](src/edit/markup/formatOperations.ts)) replaces only those four commands, keeping their bindings and their localized descriptions, and it must come **before** the borrowed ones in the dispatch list or it never runs. Its ranges are `[anchor, focus]` and so may descend, which is `expandInline`'s own convention and which `spanOf`, `caretFieldSelection`, and `getRangeOutline` all already normalize. **An unmatched keystroke bubbles out of the editor by design** — that is how the app's global shortcuts keep working from inside one — and `Control+Home` is the timeline's step-to-the-beginning, which stepped the evaluator, remounted the chat composer, and discarded the message being written; binding Control+Home/End here (reusing the already-translated `sourceStart`/`sourceEnd`) is what closes it. And **Enter must continue a bullet**, ending the list on an empty one: without it a creator who made one bullet invoked the command again for every item after it, which is exactly the syntax the feature exists to stop people learning. Ending the list must leave a *paragraph* break rather than the single newline that separates items, or whatever comes next belongs to the last bullet. It declares `typing` for `InsertLine`'s reason — the browser's own edit of the mirrored field is the screen-reader echo — and declines off a bulleted line so `InsertLine`, further down the list, still inserts an ordinary break.

**A soft-wrapped token's caret is measured, not computed.** `CaretView` placed the caret at the token box's inline start plus the width of a `Range` from the token's start — both **union** boxes, so the moment a token wraps, the caret lands on the first line at the widest line's width. Measured in Chromium over a wrapped token: wrong at 28 of 45 caret offsets. `locateCaretRect` ([measureTokenSegment.ts](src/components/editor/highlights/measureTokenSegment.ts)) asks for the collapsed caret position directly instead, and takes the **last** rect the range reports: at a wrap boundary the browser returns two (the end of one line and the start of the next), and a caret position is an index whose character *follows* it, so the caret belongs on that character's line. This barely shows in code, where tokens are short and `NodeView` emits `<wbr>` between them; it is structural in markup, where a whole paragraph is one `Sym.Words` token.

**The editor's geometry is inline-axis geometry, and one projection carries every writing mode.** Caret placement, row clustering, selection outlines, and pointer hit-testing all read physical `.left/.top/.right/.bottom`, and used to branch on an RTL flag beside a hard-coded `const horizontal = true`. [axes.ts](src/components/editor/util/axes.ts) replaces both: `Axes.rect`/`point` project viewport geometry onto a logical basis — `inline` along the text, `block` across the lines, **both increasing in reading order in every mode** — and `place`/`box`/`size` project back once, where CSS is emitted. The monotonicity is what lets the algorithms in between keep every `<`, `Math.min`, and sort comparator untouched, and it is why RTL stops being a separate mechanism: a right-to-left inline axis is a negated projection, nothing more. Three consequences worth keeping. `rowModel.ts` needed no algorithmic change at all, because it was already this algorithm named physically. `CaretView.computeLocation`'s twelve `horizontal ? …` branches were **deleted rather than fixed** — their vertical arms added a height to an x-coordinate (`bottom: priorTokenLeft + caretHeight`) and had never run, so switching them on was never an option. And `outline.ts` is the exception that proves the rule: its row tracer is pure geometry over rectangles, so `rowFrame` transposes into the frame it already works in and transposes the emitted path back, leaving the horizontal path byte-identical. **Arrow keys are remapped, not re-bound**: `remapArrowKey` translates a keystroke into the horizontal key with the same *meaning*, so every command keeps its behavior and its localized description in 30 locales and only which key invokes it moves — and it deliberately skips Control/Alt arrows, which are bound to stepping the evaluator and incrementing literals rather than to text motion. **Every projection over code comes from that code's own writing layout, never the reader's interface setting** — `CommandContext.writingLayout`, not `Settings.getWritingMode()`. The four visual line-move commands built their `editorAxes` from the interface's, which is the *default* pairing for a vertical Japanese source, and the failure mode is invisible rather than obviously wrong: `gatherTextRows` clusters token views by physical y, so in vertical text it groups glyphs *across* the columns instead of along one, and which position a line move lands on is then decided by raw glyph advances — which is why it reproduced only on WebKit, where Japanese metrics round differently from Blink's. A PR would not have caught it either: PRs run chromium only, and WebKit runs nightly.

**The editor's layout comes from the code, the interface's from the reader, and conflating them was the mistake.** A project written in Latin only makes sense horizontally whatever language its reader has chosen, so `eligibleWritingLayouts` ([src/edit/eligibleWritingLayouts.ts](src/edit/eligibleWritingLayouts.ts)) reads the *glyphs* of a source and returns what it could be set in; the toolbar offers those and the creator picks, per project and source (`SourceWritingSetting`). Nothing is imposed, and a stored choice is re-checked against eligibility on every edit — typing a Latin name into a Japanese program takes vertical away there and then. Four traps make the naive version silently useless, each with a regression test: **`ƒ` and `ø` are Latin letters** (Wordplay's own syntax, excluded by scanning only `Name`/`Words` tokens); **a unit's `m` lexes as a `Name`** (so `Dimension` leaves are skipped — `1.5m` would otherwise disqualify every program that measures anything); **`ー` is `Script=Common`**, so `\p{scx=}` and never `\p{sc=}`, or `フレーズ` reports "not Katakana" and Japanese is never eligible; and **ISO's composite codes** `Hans`/`Hant`/`Kore` are not Unicode script values at all, so they are skipped and resolve through `Hani`/`Hang`. The signal is orthographic on purpose: `Project.getLocalesUsed()` misses untagged text, and a locale is not a script — Serbian is written in two alphabets.

**The writing layout is offered only where it means something, and `verticalLayout` is neither `layout` nor a boolean.** `layout` is a script's *modern default* and is correctly `horizontal-tb` for CJK; `verticalLayout` names the one vertical mode that script is actually set in. It has to be a layout rather than a flag: CJK runs its columns right-to-left and Mongolian left-to-right, no script uses both, and a boolean offered a Japanese reader `vertical-lr` — a direction nothing they read is set in. The `Mode` widget's `omit` drops the other option. Conflating them would make `auto` resolve Japanese to vertical, which is wrong. The setting gates on `Locales.supportsVerticalLayout()` — true when **any** chosen locale qualifies, not the primary, so someone writing in English and Japanese still gets the choice. `resolveWritingLayout` is the only thing anything reads: it returns `horizontal-tb` whenever the gate is closed **without disturbing the stored value**, so dropping the locale that offered the control also stops it applying, and re-adding the locale restores the choice — otherwise a creator is left with a vertical interface and no control to undo it. It reaches the DOM as `data-writing-layout` on `<html>`, and surfaces opt in through the global `reading-surface` class; setting `writing-mode` on `:root` instead would turn toolbars, the tile manager, and pickers sideways, which is never what anyone wants. **The line is between reading and operating**, and putting it in the wrong place is the mistake to avoid repeating: applying the mode to `MarkupHTMLView` sounded right — it *is* the prose renderer — but markup also renders every settings row, dialog explanation, notice and tooltip, and no Japanese application sets its settings dialog vertically. Markup therefore declares no writing mode; the long-form reading surfaces declare it and markup inherits: a concept's documentation, a how-to's answer, the guide's introduction, a lesson's turns, a static page's prose. Two rules, both learned by measuring. The test is "would someone read this at length", not "is this prose" — a settings dialog is prose and is somewhere you operate. And the mark goes on **each prose block**, never on a pane that also holds card listings, because **a block inside vertical text is laid out within a column**: a grid placed there is bounded by a column's width whatever writing mode it declares for itself, which took the concept listing from 1248px wide to 38. Opting the grid out does not rescue it; keeping it outside the surface does. **A vertical block needs three things horizontal prose gets for free**, and a *second* class, `reading-pane`, supplies each: a **measure** (`inline-size: min(40em, 80dvh)` with `flex: none` — a maximum is not a size, a box that takes its height from its content collapses with it, and `flex: 1` beats `inline-size` on the parent's main axis; capping to `100dvh` instead gave a ~1500px line on a tall window that never wrapped), a **bound** on the other axis, and **its own scroller** — columns grow toward *decreasing x* and no left-to-right ancestor can scroll that way, so the overflow is otherwise unreachable while `scrollWidth` reports nothing wrong. The split is load-bearing: `reading-surface` says "this is prose" and `reading-pane` says "and it fills the window", which is false of a lesson's dialog — sizing that from the viewport put a 640px block inside a 378px dialog and made the tutorial unreadable. **And vertical text takes its line length from the block's *height*, which is the opposite of what stacking the tutorial's dialog assumed**: the full-height 20-30em column it already occupied gives a ~47-character line where a wide strip gave 12, so the vertical layout keeps the default side-by-side arrangement and only wraps the prose in a `.lines` block, so the writing mode lands on it without taking the nav row above it — a flex row in vertical text runs *down* the page, which turned `← title →` into a 1083px-wide stack. Code inside vertical prose opts back out the way `RootView` does: `ExternalExampleView` declares `horizontal-tb`, since a Python listing on its side is unreadable and its line breaks mean something. **`RootView`'s own `horizontal-tb` has to be overridable, because the editor renders its code through it** — that rule reached inside the editor and forced the code back horizontal while the editor element itself still reported vertical, so the whole feature was dead and every test passed, each of them measuring the container rather than the code. The editor now passes a `layout` prop; everywhere else leaves it undefined and gets the horizontal default. **And the surface is opt-in per page, never on the wrapper**: `Writing.svelte` backs eighteen routes and most of them are listings (`projects`, `galleries`, `characters`, `teach`) or forms (`login`, `join`, `profile`, `localize`) — places you *operate* — so marking the wrapper turned all of them vertical and collapsed `/projects`' grid to zero pixels, the column rule again. Six pages pass `reading`. Viewport units are physical and unaffected by writing mode, which is why they can bound the axis being sized. The class is `reading-surface`, not `reading`: `Speech` already uses `reading` positionally, and a global unscoped rule turned every palette and annotation bubble in the app vertical. And chrome nested **inside** a text surface must opt back out: the editor's search panel pins itself with `align-self`/`order`, which are flow-relative, so it landed in the wrong corner until it declared `horizontal-tb`. Output is deliberately **not** governed by it: `RenderContext.layout` comes from the *project* locale, so a viewer's preference can't re-lay-out someone else's composition, and a creator makes a phrase vertical with its own `direction` (#220). Two costs the projection introduced and does not have to pay: `Axes` carries scalar `blockStart`/`blockEnd`/`containsBlock` beside `rect`, because the pointer code tests every token view in the source on every move of a drag and projecting before filtering turned a zero-allocation comparison into three objects per token; and `eligibleWritingLayouts` is memoized on the `Source`, which is safe because a source is immutable and necessary because the editor and its toolbar both derive it on every keystroke. `npm run rtl` now guards two tiers — inline-axis properties everywhere, block- and scroll-axis properties on the `TEXT_SURFACES` list — with a `/* physical: reason */` comment exempting the run of declarations it introduces, and [logicalCssSync.test.ts](src/util/logicalCssSync.test.ts) runs it in `npm test`, since it was red on main for some time precisely because nothing ran it.

### Accessibility

The project's standard is **axe-detectable WCAG 2.2 Level AA** (axe tags `wcag2a wcag2aa wcag21a wcag21aa wcag22aa`), enforced in CI and as a deploy gate:

### Screen-reader announcements

All dynamic announcements to screen readers must go through the centralized [Announcer.svelte](src/components/project/Announcer.svelte), which owns the app's single live region. Do **not** add component-local `aria-live` divs — they conflict with the centralized region and cause cross-talk on real screen readers ([ariaLiveConvention.test.ts](src/util/ariaLiveConvention.test.ts) enforces this).

The Announcer owns **two** regions. The **immediate** one (assertive) carries the direct answer to a keystroke — typing echo, caret movement, rejected edits — and holds nothing, so each keystroke replaces the last. The **paced** one (`role="status"`, implicitly polite) carries everything else, held for its reading time so a burst of status can't talk over itself. Both live in Announcer.svelte, so the one-owner convention still holds.

Two VoiceOver behaviors shaped this, both found by testing and neither obvious from the spec. **Assertive regions chime**: VoiceOver plays its system alert sound for `aria-live="assertive"`, with or without `role="alert"` — and a live region is simply the wrong instrument for character echo (polite drops characters at typing speed; assertive chimes on every one). So editor character echo is **native** (#1248): the hidden `keyboard-input` textarea mirrors the source text and caret selection, and echo-bearing keystrokes (plain characters, Enter, single-character Backspace/Delete at a position) skip `preventDefault` so the browser's own edit of the field is what the screen reader echoes — immediate, chime-free, correctly interrupting. The keydown command still applies the model edit; `skipNextInput` keeps the input event from applying it twice, and the mirror resyncs on every model change (suspended during IME composition, which runs in an emptied field). The `type` announcement kind remains only for echoes that can't route natively (tab insert, single-character node deletions) and is paced, not assertive. **The mirror is a unit conversion, not just a copy**: a caret position counts *graphemes* (`Source` builds `tokenPositions` from `UnicodeString` lengths) while `setSelectionRange` counts UTF-16 code units, so `syncMirror` converts through `UnicodeString.getCodeUnitPosition` — handing the raw position over put the field's caret inside the surrogate pair after any emoji, and Wordplay names things with emoji constantly (#1329). The same `UnicodeString` the field's value came from is the right basis precisely because it is already normalized; `measureTokenSegment.ts` avoids `UnicodeString` for the mirror image of that reason, since it indexes raw DOM text. Converting is only needed on the write side: the mirror is strictly one-way, and every edit is derived from `event.data`, `input.value`, or the clipboard, never from the field's own selection. **An unchanged region is silent, and nothing makes it speak again**: replacing the node, clearing and restoring on a microtask, and clearing with a real 100ms gap were all tried against VoiceOver, and all stayed silent.

**So every recurring announcement must vary its text, or it is heard once and then sounds broken.** This is the single easiest mistake to make here — it has been made three times, each in a feature whose whole purpose was to describe something that repeats. The rule to apply when writing any announcement that can fire more than once: **ask what in this string changes between two consecutive firings.** If the answer is "nothing," the announcement is silent from the second firing onward, no matter how correct it reads. Watch especially for summaries, which are constant *by construction* — a count plus a label ("12 outputs changed in my grid") is the same words every time. The fix is always to name what actually differs:

| Announcement | Constant form (silent after one) | What varies, and now rides along |
| --- | --- | --- |
| Stage output value | "Face" every evaluation | the property that changed — "eyesOpen true" ([describeChange.ts](src/values/describeChange.ts)) |
| Output moved | "moved, cat moved left" per keypress | the destination — "…to −2m 0m" ([direction.ts](src/components/output/direction.ts)) |
| Many outputs changed | "12 outputs changed in my grid" per tick | one example — "…, like 5" ([OutputDescriptions.ts](src/components/output/OutputDescriptions.ts)) |

Two supporting rules fall out of this. Numbers round to tenths, so imperceptible precision isn't announced and doesn't count as "varying". And nothing changed means nothing is said — silence is the signal for no change, not for a broken app. Cover it with a test that fires the announcement twice over different state and asserts the two strings differ; asserting one call's content passes happily while the feature is inaudible.

**Snapping compares siblings in one frame, and every constraint has to be audible.** Moving output on stage snaps to the grid and to other output's edges, centres, and baselines (#117, [snap.ts](src/components/output/snap.ts)). Four things are load-bearing. Candidates are the moved output's **siblings under the same parent**, compared in that parent's local coordinates — the frame its `place` bind is written in; comparing accumulated globals would line up things that only look lined up, and `Place.offset` composes `y` by *subtraction*, so it is not the accumulator to reach for. The scene comes from laying the stage out **on demand**, never from `Animator.scene`, which is empty exactly when it's needed: the animator is suspended whenever the stage is paused, and paused is the only state output can be edited in. A **baseline** comes from `getLayout`'s `ascent`/`descent` and the `line-height` `PhraseView` actually paints, never from `FaceMetrics` (which carries only x-height ÷ cap-height), and it only ever pairs with another baseline — a bottom edge landing on someone else's baseline is a coincidence, not an alignment. An axis the parent arrangement **overrides** (a `Row` computes its children's x, a `Stack` their y, a `Grid` both) is never snapped or announced, or a screen reader is promised an alignment the next layout throws away. And the snap announcement carries the target's name *and* the coordinate for the reason in the table above: "aligned left" is the same words every time and would be heard once.

**Exactly one describer speaks per change.** Output has two: `OutputView` summarizes the value and its deltas, and `StageView` says what entered, changed, and moved ([OutputDescriptions.ts](src/components/output/OutputDescriptions.ts)). When a value renders as a stage, `StageView` owns it and `OutputView.describeValue()` bails — the same bail it makes for `Say`, which speech synthesis already voices. Both bails exist because two describers of one change are heard as the same sentence twice. Both are gated on `playing || stepping`: a paused stage is a preview of code being read with the caret and echo announcements, and describing it talks over them and over the tutorial's dialogue.

**Every announcement kind has a priority lane**, registered in [announcerQueue.ts](src/components/project/announcerQueue.ts) (the unit-tested queue policy behind the component). Adding a kind means adding it to the registry there and choosing a lane — an unregistered kind is a compile error. Mark a kind `immediate` when it answers a keystroke:

| Lane | Semantics | For |
| --- | --- | --- |
| `echo` | immediate, no dedupe — two of the same key are two events | per-keystroke character echo (`type`, `keyinput`) |
| `interrupt` | presents immediately, clears coalesced state, re-presents identical text; queued/echo preserved | failures: rejected edits (`ignored`), app errors (`banner`) |
| `queued` | FIFO, never dropped, reading-time paced, consecutive-dup dedupe | discrete action results (`fold`, `selection`, `tutorial-dialog`, …) |
| `coalesce` | one latest-wins slot per kind; `caret` is immediate, the rest paced | continuous streams (`caret`, `value`, `color`, stage/drag updates) |

Drain priority is interrupt → echo → queued → coalesce; queued-before-coalesce guarantees a continuous stream can never starve discrete feedback.

To announce from any component:

```ts
import { getAnnouncer } from '@components/project/Contexts';
// ...
const announce = getAnnouncer();
// In an event handler or `$effect`:
if (announce && $announce) {
    $announce('fold', $locales.getLanguages()[0], message);
}
```

**Every editor command must be audible.** A keystroke that produces silence is indistinguishable from a broken app. Commands that move the caret or edit the code are covered by the caret and echo announcements; every other command declares a `feedback` ([Commands.ts](src/components/editor/commands/Commands.ts), [feedback.ts](src/components/editor/commands/feedback.ts)) — either a localized confirmation, or one of `'caret'`/`'echo'`/`'focus'`/`'delegated'` naming what speaks instead. There is no way to declare silence and no way to pass a raw string. `Commands.test.ts` fails any command that declares nothing, and enumerates by name the commands claiming `'focus'`/`'delegated'`, so those claims get reviewed. All three dispatch paths announce — the editor's keydown, ProjectView's window handler, and CommandButton — so a command sounds the same however it's invoked.

**A cue is a sound, not a sentence, and it names the stream that caused a re-evaluation.** Audible evaluation cues (#537, [src/output/Cues/](src/output/Cues/)) are deliberately not announcements: a constant string like "re-evaluated" is heard exactly once (see the varying-text rule above), and speech is far too slow for a per-event cue. Three invariants. The sound table is **total over `StreamKind`** — the discriminant every concrete `StreamValue` declares, since `instanceof` can't separate the family classes and a definition's names are locale data — so a new stream is a type error until it has a sound. Cues connect to the audio destination **bypassing the music master**, so they are never ducked, never scaled by the music volume setting, and never squashed by the mix limiter: a viewer's accessibility cue is not the creator's to quiet, and the timbres stay off the 12-TET grid so a cue is never mistaken for a note in the program's own composition. And each kind has a **floor** — a minimum spacing — whose overflow is *dropped, never queued*, because a cue arriving after the event it names describes the past; a keypress therefore cues every time while a pointer move or a `Time()` tick is capped. `EvaluationCues.svelte` is mounted only by `ProjectView` (not `PlayView`, which the landing-page showcase and tutorial also use), fires in play and while stepping across inputs in debug, never in edit, and is off by default per device.

**A physics contact is cued whether or not the program is watching for one.** Cueing only re-evaluations meant a stage full of bouncing output was silent unless the creator had written `Collision()`: `Physics.report` hands every contact to the Collision streams, and a program with none discards them all — Hiragana's 32 falling letters made no sound at all. `drainCollisions` now also reports contacts to [contacts.ts](src/output/Cues/contacts.ts), a listener registry keyed by evaluator (so a docs page's previews can't cue a creator's project) holding neither `@db` nor Web Audio (so Physics stays testable in Node). Four consequences worth keeping. The strength comes from `manifold.contactImpulse` **inside the `contactPair` callback that is already open** — the velocities readable after the step are the ones the collision just changed, so a body that landed and stopped dead would measure as nothing. Only `starting` contacts are cued, since Rapier fires on begin *and* end, and only above a strength threshold, since a resting body's support impulse is not zero. The normalizing constant is **measured, not derived** (Rapier's units here reproduce Matter.js's feel rather than SI): 3000, the 95th percentile of Hiragana's landing. And `collision` is the one **polyphonic** cue — the loudest four of a burst sound together at varied pitch and gain, because a landing is four things landing, where the reaction path's collapse-to-one is right for a stream that merely fired repeatedly. The reaction path therefore skips kind `collision` entirely: the contact is the event, the reaction is its consequence, and cueing both sounds one bounce twice. The cue bus carries its own limiter, since polyphony makes its sum unbounded.

**An animation is cued from what its poses do, and the mapping is deterministic so that repetition is audible.** Animation was the one thing a stage does that made no sound: a resting `Sequence` drives one long-lived Web Animation and never re-enters the evaluator, so the Christmas tree — whose entire behavior is a looping sequence — had nothing for any cue to name. `OutputAnimation.start()` now reports each tween to [figure.ts](src/output/Cues/figure.ts), which turns the poses into a figure: rotation bends the pitch, `offset.x` pans, `offset.y` and `scale` move the pitch, `opacity` scales the gain (so a `fadeout` ends in silence), and color opens the tone (so `rainbow` and `glow`, which change nothing else, aren't silent). Five things are load-bearing. **`start()` is the seam precisely because `retarget()` bypasses it** — the optimization that stopped rebuilding a WAAPI animation every frame is also what keeps a physics stage from cueing its animations on top of its contacts. **The first transition is never cued**: it is where the animation starts, not somewhere it arrives (`compile` gives it no duration, `rest` prepends the pose already held), and sounding it would announce the end of the last loop at the start of the next. **Each output's base pitch is a hash of its name**, so two animating outputs are distinguishable and each keeps one voice — and identical inputs give an identical figure, which is what makes a loop heard as a phrase recurring rather than noise recurring (`figure.test.ts` asserts exactly that). **A pose that changes nothing is silent**, the announcements' rule again. And because a figure is scheduled a whole iteration ahead on the audio clock — there being no per-frame moment to hang a cue on — a pause or a cancel must be able to **take back** what hasn't sounded, which is what `soundFigure`'s handle and `cancelAnimation` are for. **Each source has its own switch, and none is a master.** `gateOf` ([cues.ts](src/output/Cues/cues.ts)) is total over `CueEvent` and sorts every cue into `evaluation`, `contact`, or `animation`, which the three settings rows govern independently — a row that means anything other than exactly what its label says reads as broken. The split follows what the sources actually are rather than where they came from: a contact is not a re-evaluation (it sounds whether or not the program evaluates `Collision()`), an animation is continuous where the others are events, and the rates differ by an order of magnitude — a landing is twenty cues in a second where a keypress is one. Only a contact ever schedules kind `collision`, which is what lets `gateOf` key on it.

**`StreamKind`'s other job: an input is only replayed into the same kind of stream that recorded it.** `Evaluator.mirror` replays each recorded raw input into whatever stream its `Path` resolves to in the revised program — and a `Path` is `{type, index}[]`, so it cannot tell two `Evaluate`s apart. Typing a new stream above an existing one shifts every later index, and an input arrives at a different stream. That is not a near miss, because every `react` trusts its own raw type: a `Key` event handed to `Speech` reached `text.normalize()` on an object and threw during evaluator construction, while a `Pointer` event handed to `Placement` would have quietly produced nonsense. Each input records its stream's `kind`, and a mismatch stops the replay the way every other unresolvable case in `mirror` does ([replayKind.test.ts](src/runtime/replayKind.test.ts)).

Announcement text is **primary-locale-only** — use `getPrimaryPlainText`, matching the `lang` the region declares. `aria-label` on a focused element is still appropriate for _focus-time_ labeling — screen readers read the label when the element receives focus. Use Announcer for _change-time_ announcements (the user moved a slider, picked a color, toggled a setting).

### Testing

**What each level costs, measured.** The default vitest run (`fast` + `isolated`) is 504 files and 8,673 cases in about **15 seconds**; 440 of those files finish under 200ms and account for 7.2s between them, so an ordinary unit test is free and you should never weigh its cost. A Playwright test costs about **5 seconds on CI** — 1,472 test-seconds over ~275 tests across three shards — and almost none of that is the assertion: navigation and hydration are 3-4s before a single thing is checked, which is why the e2e distribution has no dominating test and 146 of them sit between 2 and 5 seconds. That is a **~170× ratio**, and it is the whole argument for where a test goes. Cheapest of all is a spec that needs no browser: [page-preview.spec.ts](tests/end2end/page-preview.spec.ts) gets 8 tests in 1.4s by `fetch`ing the hosting emulator.

**Put a test at the cheapest level that would have caught the bug.** The parser, the analyzer, the evaluator, `src/edit/**` and every locale-tooling module are pure and testable in milliseconds — a bug in any of them found by an e2e test is a bug that took 5 seconds to find instead of 30ms, and reported against a page instead of a function. Reach for a browser only when the claim is *about* the browser: hydration, focus order, a live region reaching a screen reader, computed color, CSS geometry and writing mode, IME, clipboard, animation timing, or a Firestore round-trip through the real client. [writing-vertical.spec.ts](tests/end2end/writing-vertical.spec.ts) states the bar correctly in its own docstring — "`getBoundingClientRect` is zero in JSDOM". Cheaper than any of it is a **convention test** ([testIsolationConvention](src/util/testIsolationConvention.test.ts), [Commands.test.ts](src/components/editor/commands/Commands.test.ts), [logicalCssSync](src/util/logicalCssSync.test.ts), [ariaLiveConvention](src/util/ariaLiveConvention.test.ts)), which costs nothing and closes a whole class rather than one case.

**Adding an e2e test.** Each of these is worth 3-5 seconds a test, every run, forever. *Add an assertion to a spec that already has the app in the state you need, before adding a `test()`* — a new test is a new page load even when it checks one attribute, which is why the axe specs navigate once and check both color schemes on the one page (`expectNoAxeViolationsInBothSchemes` in [checkAccessibility.ts](tests/helpers/checkAccessibility.ts)) and why eight nav-link tests became one. *Use the worker-scoped fixture* in [playwright/fixtures.ts](playwright/fixtures.ts), which signs in once per worker; `loginNewContext` builds a context and restores Firebase Auth's IndexedDB per call, so it is for tests that genuinely need a second identity. *Never `page.waitForTimeout`* — a web-first assertion or `expect.poll` is faster when it passes and clearer when it fails; the only defensible sleep is a window in which you are asserting that something does **not** happen, and it needs a comment saying so. *A new route is one line in `PUBLIC_ROUTES`*, not a new spec. And check `reportSlowTests`, which now names anything over 20s: the CI gate is the slowest of three shards, not their sum, so one heavy spec costs more than its own seconds.

**Adding a unit test.** Default to `src/**/*.test.ts` in the `fast` project. A file calling `vi.mock` must be listed in [isolatedTests.ts](src/util/isolatedTests.ts) or its mock leaks into every later file in the same worker. Two file-level costs are worth knowing, because **vitest parallelizes by file and runs a file's tests sequentially in one worker**: a `test.each` over thousands of corpus cases pins one lane that no amount of CPU shortens — `localizedExamples.test.ts` at 2,181 cases *was* the entire suite's wall clock, running from t=2.4s to t=76.7s while every other file finished by t=55.8s — and a file of four monolithic tests cannot spread across lanes either, so prefer `test.each` to a loop inside one `test()`. If a test's cost scales with `static/examples/**` or `static/locales/**` rather than with the code under test, it is a **sweep**: mark it `@sweep <corpus root> <reason>`, list it in [sweepTests.ts](src/util/sweepTests.ts), and [sweepConvention.test.ts](src/util/sweepConvention.test.ts) holds the two together. A sweep does not run in `npm run test:run`; the pre-commit hook runs it for the corpus you staged and the `sweep` CI job runs it whole.

**When to run what.** The full suites are a gate, not a feedback loop.

| Moment | Run | Why |
| --- | --- | --- |
| While iterating | `npx vitest run <path>` on the file you're editing | Sub-second. `npm test` is watch mode over everything and never exits. |
| Before declaring a change done | `npm run check:now` and `npm run test:run` | ~15s and ~70s. Rule 5 below. Add `npm run test:sweep` only if you touched `static/examples/**`, `static/locales/**`, `src/util/verify-locales/**`, or `src/examples/**`. |
| Iterating on one e2e surface | `npx playwright test <spec>`, or `npm run end2end:quick` when `build/` is current | The full suite is a ~5-minute three-shard CI gate; running it locally to check one component is not a trade worth making. `npm run end2end:failed` re-runs only what failed. |
| Before committing a user-visible change | `npm run end2end`, once, clean | Not repeatedly mid-session. `end2end:reuse` skips the reseed against a long-lived `npm run emu` emulator, but accumulated emulator state makes both suites flaky, so it is an iteration tool and never the thing you declare done on. |
| Accessibility work | `npm run build && npx firebase emulators:exec "npx playwright test accessibility keyboard-navigation aria-snapshots announcer --project=chromium" --project=demo-wordplay --log-verbosity QUIET` | The one e2e subset worth running whole; also in the Accessibility section. |

Locally Playwright runs four workers, not a fraction of the cores (`PLAYWRIGHT_WORKERS` overrides): the shared resource is the single-process Firestore emulator, and measured over the eleven cloud-assertion tests that contend hardest, 2 workers failed 2, 4 failed 1, and 7 failed 4. If a run goes flaky, lower it before suspecting the change.

### Behavior

1. Don’t assume. Don’t hide confusion. Surface tradeoffs.
2. Minimum code that solves the problem. Nothing speculative.
3. Touch only what you must. Clean up only your own mess.
4. Define success criteria. Loop until verified.
5. After every code change, run `npm run check:now` and `npm run test:run` — **not** `npm test`, which is vitest in watch mode and never exits. Both must pass before declaring a change done: IDE-reported diagnostics are not a substitute for a clean full type-check, and unit tests catch regressions in branches that hand-testing misses (especially environment-sensitive code like UA sniffing, where JSDOM and the locale verifier's tsx runtime differ from the browser). What a change owes beyond those two — and, just as importantly, what it does not owe on every iteration — is in **Testing** above.
6. Always resolve all TypeScript errors, and never use `as`.
7. When you finish a user-visible change (anything touching `src/components/**`, `src/routes/**`, `src/output/**`, or a new built-in feature/dialog/output type), ask the user once at the end: "Want me to draft a CHANGELOG entry via `/changelog`?" Skip the prompt for refactors, test-only edits, doc-only edits, comment edits, and dependency bumps. Never invoke `/changelog` without the user's confirmation. Two rules govern what an entry may be, and both exist because **every entry is machine translated into 29 languages**: it is **one sentence** (a second only when the first would be untrue without it), and it describes **only what a creator can see** — the test is "could a teacher or a student notice this without reading the code?", which excludes refactors, internal architecture, CI and tooling, imperceptible performance work, and accessibility plumbing that changes no behavior. Editing a published entry buys 29 new translations, so fix a wrong one freely and never reword one for style.

### Comments

When writing comments, focus on rationale for a behavior, but keep it to 1-2 sentences.
